# v1.4 architecture outcome review

## Scope and verdict

Review of Ledger's actual v1.4 outcome against its original goal: keep the app as simple, lightweight, clean, and native an AppKit app as possible ahead of v2.0.

Reviewed Ledger HEAD: `7045faf`, the checklist-signoff commit following the manually tested `73c1ed8`. Ledger and sibling SharedUI were on branch `v1.4`. This was a source/document review: no application launch, fresh test run, performance capture, or implementation changes were performed. Line numbers below refer to the reviewed checkout and may move.

Read in order:

1. `v1.4-architecture-plan-2026-08.md`
2. `v1.4-performance-audit-plan.md`
3. `v1.4-progress.md`, including the full historical decisions and corrections
4. `archive/v1.4-review-fix-handoff-2026-09-25.md` (moved to `docs/archive/` once v1.4 shipped) and `v1.4-manual-smoke-checklist-2026-09.md`
5. The relevant Ledger and SharedUI implementation

**Verdict:** v1.4 is genuinely AppKit-first and substantially cleaner than it started, but it does not fully satisfy its own completion criteria. The native shell largely holds up; lifecycle and background-work ownership still have concrete gaps. Some completion claims in the progress document exceed what the implementation or evidence establishes.

This is a successful native-shell cleanup with unfinished pipeline and lifecycle hardening. The missing Observation migration and rejected write batching are not the reasons to withhold an unqualified pass. The observer lifetime defects, synchronous menu discovery, incomplete cancellation, and hidden-mode metadata demand are.

## Material findings

### R1 — Observer installation and teardown still use mismatched lifetimes

**Classification:** concrete source-level correctness issue; missed architectural work rather than an optional optimisation.

The final fixes repaired reinstallation in the browser container and main controller, but the same defect remains elsewhere:

- `Sources/Ledger/EOS1V/EOS1VDeviceViewController.swift:264`: `EOS1VConnectViewController` subscribes to session changes in `viewDidLoad`, removes the subscription in `viewWillDisappear`, and never reinstalls it. Switching from Connect to another native tab and back leaves its connection/status UI without ongoing session updates.
- The enclosing EOS controller has the same pattern at lines 74–94.
- Sibling `SharedUI/Sources/SharedUI/List/SharedBrowserListViewController.swift:102` removes column persistence observers on disappearance but installs them only during initial configuration. After a genuine disappear/reappear cycle, column changes stop reaching those handlers.

The early progress log calls `viewDidLoad` installation plus `viewWillDisappear` removal a consistent convention. These are not matching lifetimes for retained controllers. The later review recognised that mistake without completing its scope.

**Implementation direction to evaluate:** use one coherent lifetime per resource: guarded appearance/reappearance installation with disappearance teardown, or object-lifetime installation with appropriate final teardown. Avoid a generic lifecycle framework. Verify the actual tab and retained-controller paths, including no duplicated callbacks.

### R2 — Menu validation still performs synchronous filesystem/application discovery

**Classification:** direct violation of the execution plan's synchronous interaction-path rule; no fresh stall measurement made in this review.

`Sources/Ledger/AppModel+Actions.swift:363`, `fileActionState`, eagerly resolves the default application and both Lightroom variants before switching on the requested action. Helpers perform filesystem checks, bundle reads, and `NSWorkspace` queries.

As a result, validating even Apply or Discard can perform unrelated external-application discovery. `Sources/Ledger/MainContentView+Menus.swift:774` calls this helper repeatedly. Opening File also discovers compatible applications and retrieves names/icons synchronously (`makeOpenWithSubmenu`, line 373).

Keeping `menuWillOpen` instead of `menuNeedsUpdate` is a reasonable documented choice. It does not resolve the underlying work on the synchronous path.

**Implementation direction to evaluate:** compute only what an action requires and use appropriately refreshed availability/menu data. Keep native menu/responder-chain ownership; do not invent a menu framework. Verify enabled states, titles, shortcuts before first menu opening, and behavior when external-app availability changes.

### R3 — Cancellation remains incomplete beneath model task handles

**Classification:** load-bearing gap against the cancellation/idle gate, separate from write batching.

`LedgerCore/Sources/LedgerCore/ExifToolService.swift:307`, `run`, polls until completion or timeout without checking task cancellation. Defaults remain 12 seconds for reads and 25 seconds for writes.

This also weakens the model's eight-second metadata timeout. `Sources/Ledger/AppModel+MetadataPipeline.swift:267`, `readMetadataWithTimeout`, races work inside a throwing task group, but the group must await the cancelled child's completion. Cancellation does not forcibly stop the subprocess. See [Apple's task-group lifetime documentation](https://developer.apple.com/documentation/swift/withthrowingtaskgroup(of:returning:isolation:body:)).

Preview ownership has related gaps:

- `requestInspectorPreviewFromThumbnailService`, around line 245, creates a detached task without forwarding cancellation.
- Preview callers can publish returned images and clear per-URL task bookkeeping without checking whether a newer request has replaced them.
- Cancelling a caller should not be confused with cancelling shared broker work or interrupting an already-running synchronous decode. The broker's existing permit accounting must continue tracking physically running work accurately.

Closing the main window while Settings/Console remains open need not terminate the process. The review-fix handoff explicitly leaves model-work cancellation on close unresolved.

**Implementation direction to evaluate:** distinguish obsolete reads/speculative previews from user-authorized writes. Propagate cancellation where appropriate, protect publication and cleanup with request ownership, and define close/reopen behavior. Preserve partial-write reporting, backups, restore, shared-request semantics, and concurrency bounds. Do not implement indiscriminate subprocess termination or introduce a persistent ExifTool service merely to fix cancellation.

### R4 — Metadata demand includes hidden modes and remains folder-wide

**Classification:** explicit implementation policy that conflicts with the stronger visible-demand/lightweight goal.

`Sources/Ledger/AppModel+FileLoading.swift:519`, `hasVisibleMetadataColumnDemand`, considers persisted List columns even while List is hidden, and icon subtitles regardless of active mode. Once enabled, prefetch scans the folder in enumeration order rather than prioritising visible rows.

The progress log's contamination investigation measured approximately 34 seconds of work and 127 ExifTool launches on the corpus with metadata preferences enabled. Those preferences contaminated the intended no-demand benchmark, but the workload represents a real supported app configuration.

Deferring viewport prioritisation for opt-in metadata columns was an explicit proportionality decision. Treating a hidden mode's preference as visible demand is less consistent with the governing principles. The lightweight claim is well supported for the default configuration, not generally established across supported configurations.

**Implementation direction to evaluate:** distinguish the small active-mode demand correction from a larger viewport scheduler. Ensure enabling a metadata column/subtitle or switching modes triggers required loading after the folder is already open. Keep selected-file metadata responsive and prevent stale values. Measure before undertaking more elaborate prioritisation.

### R5 — Explicit active-controller routing does not prove hidden surfaces are inactive

**Classification:** overstatement of the structural guarantee; residual work needs measurement before broader redesign.

The container correctly sends explicit updates only to the active controller. However, all three controllers are eagerly installed, and Gallery's `Sources/Ledger/LargePreviewCard.swift:9`, `LargePreviewPane`, independently observes the entire AppModel.

Hiding the AppKit view does not remove that observation relationship. The routing switch proves hidden controllers receive no explicit `update` calls; it does not prove their hosted SwiftUI content cannot invalidate.

Deferring lazy creation remains reasonable: the additional approximately 124 ms was measured, disclosed, and accepted. The stronger claim that hidden work is structurally impossible is unwarranted. This does not establish a need for Observation migration; ownership and attachment are the first questions.

**Implementation direction to evaluate:** retain the accepted lazy-creation deferral unless evidence justifies reopening it. If addressing hidden hosted work, verify invalidation/task behavior rather than assuming it from the container switch. Preserve mode-switch selection, focus, and immediate data correctness.

### R6 — Supported-OS and map-warning verification remain incomplete

**Classification:** unresolved verification; this review did not reproduce a new runtime failure.

The checklist's detailed signoff explicitly skips macOS 26 despite its “all 10 sections PASS” summary. Ledger still targets macOS 26. Some workaround removals were justified specifically by macOS 27 making the original behavior moot.

Separately, `v1.4-progress.md:2169` leaves the map-drag reentrant-layout issue unfixed after three failed attempts were reverted. The current `Sources/Ledger/DateTimeAdjustSheetView.swift:1299` MapKit bridge retains the direct drag-time binding writes described there.

The later clean Console pass is useful evidence, but contains no explicit reproduction-and-resolution of that particular drag sequence. Treat it as unresolved verification, not proof that the bug necessarily reproduced in the signed-off build. Native MapKit inside SwiftUI is appropriate; its known bridge failure needs specific closure.

**Implementation direction to evaluate:** reproduce with a separate app instance, debugger/stack evidence, and the actual drag sequence before changing code. Do not repeat speculative dispatch-delay fixes. Verify coordinate updates and staging still work. Record unavailable macOS 26 coverage honestly rather than marking it passed or silently changing the deployment target.

| Lazy List/Filmstrip creation | Reasonable accepted tradeoff with a measured cost. |
| Proportional sidebar-width restoration | Correctly rejected as unnecessary; native fixed-sidebar/content-absorbs-resize behavior is appropriate. |
| Write batching | Reasonable rejection given acceptable performance and write-path risk, subject to the rationale correction below. |
| Larger UI-test matrix and isolated preferences | Testing debt, not justification to redesign production architecture. Limits confidence in broad completion claims. |
| 20–50-folder memory/pressure measurement | Still needed to substantiate bounded-memory claims. The 5,000-entry policy protects the entire active folder and other sets, so it is not an unconditional cap. |

| Initially deferred quiescence instrumentation | Subsequently implemented; not outstanding. |

### R7 — Correct the batching rationale without automatically reopening batching

The progress log says differing per-file arguments require `-stay_open`. That is too strong: ExifTool supports multiple command groups in one invocation using `-execute`. Backup interleaving and accurate per-file result attribution still make batching nontrivial, so rejection can stand. The persistent-process-is-required premise should not guide future planning.

Reference: [ExifTool application documentation](https://exiftool.org/exiftool_pod2.html).

### R8 — Retained sidebar scroll repair lacks a current independent justification

Sibling `SharedUI/Sources/SharedUI/Sidebar/AppKitSidebarController.swift:209`, `applyInitialScrollPositionIfNeeded`, still explicitly scrolls to zero once an inset appears, although the log says toolbar-before-content construction fixed its root cause.

Its flag is used only by the repair in the reviewed file. The suggestion that unrelated bookkeeping requires retaining it is unsupported by the current implementation. This is a small example of keeping a workaround just in case, not a release-wide flaw.

**Implementation direction to evaluate:** inspect all consumers and verify launch/restoration behavior before removing it. If still necessary, document the concrete path and supported OS/build that require it. Avoid substituting another timing patch.

## Native controls and animation assessment

The window, toolbar, split views, sidebar outline, browser tables/collections, menus, and tab controller are real AppKit controls. The gallery uses native compositional layout. Selection layers and custom cells are ordinary app presentation, not fake replacement widgets.

There are authored animations: Core Animation fades, `NSAnimationContext` constraint animation, and system symbol effects. They use platform animation machinery rather than a hand-rolled animation engine. “Zero custom animation” would be inaccurate; “native” is fair.

Do not use this review to justify replacing the UI, retiring Combine wholesale, introducing generic coordinators, or undertaking the v2.0 browser rewrite early. The recommended direction is targeted ownership/correctness fixes and accurate evidence, with the smallest native mechanisms that satisfy the existing behavior.
