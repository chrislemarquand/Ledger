# v1.4 Architecture Plan — 2026-08-29

Audit of the six items currently tracked under v1.4 in `docs/Roadmap.md` and their associated docs, plus one v1.3 item that belongs in the same bucket, done against the stated goal: keep Ledger as simple, lightweight, clean, and native an AppKit app as possible ahead of the v2.0 gallery rewrite. Audit and restructuring proposal only — no code changed.

## Is the app actually "hacky"?

Worth answering directly before restructuring anything, since it's the concern driving this request. The most relevant existing evidence is `docs/appkit-ui-performance-audit-2026-07.md`'s Pass 1 verdict, done specifically against "keeping Ledger as close to a native Mac app as possible": *"disciplined AppKit-first app... no custom window chrome, no custom scrollbars, no hand-rolled animation engine... Critical: None found."* Gallery is real `NSCollectionView`, drag-and-drop is real `NSDraggingSource`/`NSPasteboardWriting`, context menus are real `NSMenu`, colors are fully semantic (zero hardcoded hex anywhere in either repo). That verdict hasn't been invalidated by anything found since.

The honest picture: the app's *rendering and interaction core* is not hacky. What's real is a **cluster of bounded architectural debt in a small number of identifiable places** — not pervasive tape-and-string, but genuine issues worth a dedicated pass:

1. Menu bar construction happens at runtime from a view controller's lifecycle instead of existing from launch (this session's menu-bar audit).
2. Window frame, split dividers, and table columns are restored via three independent, uncoordinated absolute-pixel autosave systems (`docs/window-list-resize-diagnosis-2026-07.md`, currently tracked under v1.3, not v1.4 — see below).
3. A handful of Liquid-Glass-era (macOS 26) timing/appearance workarounds of unconfirmed continued necessity on Golden Gate (SharedUI's already-detailed 7-item inventory).
4. Two large, multi-concern files (`MainContentView.swift`, some `AppModel` extensions) that make exactly the kind of mistake this session made (a function silently serving two different timing contracts) easy to reintroduce.
5. One confirmed performance bottleneck (`exiftool` spawned once per file on write, never batched) and one correctness/consistency gap partially closed this session (thumbnail disk cache not checked synchronously — quick fix shipped, wider pass still open).

That's a real, worthwhile cleanup — but it's scoped and known, not a sign the app needs a rewrite.

## The six current v1.4 items, and how they actually relate

| # | Item | Size | Depends on | Notes |
|---|------|------|------------|-------|
| 1 | `@Observable` migration + Combine retirement | Very large (~58 `@Published` properties) | Benefits from #2 first | Touches nearly every view; the biggest single risk in v1.4. |
| 2 | Performance streamlining Phase 4 (split `MainContentView.swift`, decompose `AppModel` extensions) | Medium | None | Structural prerequisite for #1 and #3. |
| 3 | macOS 26 chrome-workaround audit | Medium (7-item inventory already exists, SharedUI-tracked) | None | Joint Ledger/Librarian/SharedUI. |
| 4 | Menu bar architecture | Medium | Easier after #2 | Same class of problem as #3 — a timing workaround, different symptom. |
| 5 | AppKit/UI + perf/memory/disk audit follow-ups (batch exiftool writes, thumbnail cache eviction) | Medium, two independent sub-items | None | Backend/pipeline, independent of UI work. |
| 6 | Thumbnail pipeline audit | Medium (quick fix already shipped this session) | None | Independent of UI chrome work. |

Two things fall out of laying it out this way:

- **#3 and #4 are the same class of problem** — both are "a workaround for cross-framework/OS timing behavior that may or may not still be necessary, discovered ad hoc." Tracking them as one consolidated effort avoids duplicate investigation (both involve re-testing timing-sensitive AppKit behavior on Golden Gate) and produces one coherent verdict on "how much of our chrome-timing code is still needed" instead of two.
- **#2 is a prerequisite, not a peer.** `MainContentView.swift` is the exact file where the menu-bar injection code (#4) lives, and where this session's regression happened — a monolithic file mixing menu wiring, split-view shell, observers, and context-menu actions together is *why* it wasn't obvious that `ensureEditMenuBaseline`/`rebuildEditMenu` had two different call-time contracts (eager-at-launch vs. lazy-on-open) sharing one function. Doing the menu-bar fix on today's file structure means fixing it inside the same tangle that caused the mistake; splitting first makes the menu-bar work smaller, safer, and easier to review. Same logic applies to #1: an `@Observable` migration across a decomposed, already-cleaned-up set of files is a fundamentally lower-risk, more reviewable change than doing it against today's structure.

## A v1.3 item that belongs here

`docs/window-list-resize-diagnosis-2026-07.md` (currently tracked under v1.3 "Browse") is not a feature — it's a pure architecture defect: three independent AppKit-native autosave systems (window frame, split dividers, table columns) each restoring absolute pixel values with no awareness of each other or of current available width, one of which actively re-corrupts its own restored state on every layout pass (documented causal chain in that file). This is exactly the "held together with tape and string" pattern the user is worried about, and it has nothing to do with v1.3's actual theme (import maturity + polish). **Recommend moving it into v1.4.**

## Recommended v1.4 structure (themed, sequenced)

**Theme A — Structural decomposition (do first; everything else gets easier and safer after this)**
- Performance streamlining Phase 4: split `MainContentView.swift` (menu wiring / split-view shell / observers / context-menu actions into separate files); continue decomposing large `AppModel` extensions.

**Theme B — Chrome & window-system foundations (native-feel surface, most visible to the user)**
- Consolidated chrome/timing-workaround audit: macOS 26 Liquid Glass workarounds (SharedUI's existing 7-item inventory) **+** menu bar architecture (this session's audit) as one coordinated effort — both are "is this OS-timing workaround still needed on Golden Gate" questions, investigated together.
- Window/list-column resize fix (moved from v1.3) — same "native AppKit persistence conventions, done right" spirit; natural to do alongside the chrome audit since both touch window/layout lifecycle timing.

**Theme C — Data/pipeline hardening (independent, can proceed in parallel with A/B)**
- Batch `exiftool` writes into one invocation instead of one process per file.
- Thumbnail disk cache eviction (age/size-based).
- Thumbnail pipeline wider pass (the synchronous-paint-vs-async-data pattern audit from this session — quick fix already shipped).

**Theme D — `@Observable` migration + Combine retirement (do last, immediately before the v2.0 boundary)**
- Unchanged in substance, resequenced to run after Theme A so it's migrating a smaller, better-organized surface rather than today's monolith.

This is four themes instead of six flat bullets, with an explicit dependency (A before B and D) and one item relocated from v1.3. Nothing here changes what any individual item actually is — `docs/thumbnail-pipeline-audit-2026-08.md`, `docs/menu-bar-architecture-audit-2026-08.md`, `docs/appkit-ui-performance-audit-2026-07.md`, and SharedUI's `docs/Roadmap.md` chrome-workaround inventory all stay as the detailed source docs; this just groups and orders the roadmap-level bullets sensibly.

## SharedUI scope pulled in

Already-tracked SharedUI items that are the same "native, not hacky" concern and should move/stay in lockstep with Theme B:
- The chrome-workaround audit itself (joint by nature — SharedUI's doc already owns the inventory).
- **Sidebar inactive-window label colour** (SharedUI `docs/Roadmap.md`): unselected sidebar row text doesn't dim on window deactivation the way native sidebars do; root cause not yet found. Small, native-fidelity, same bucket.
- **`AppKitSidebarController` sidebar-cell rebuild**: replace hand-constrained icon/title/count layout (mutually-exclusive constraint pairs, magic gap constants) with a standard `NSStackView`. Explicitly framed in SharedUI's own doc as overlapping the inactive-label-colour item — do together.

None of these need new Ledger-side roadmap bullets; they're already correctly SharedUI-owned. Flagging them here only so Theme B's scope (when actually planned in detail) pulls in the SharedUI side rather than treating "chrome audit" as Ledger-only.
