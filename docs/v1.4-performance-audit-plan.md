# v1.4 Performance Audit Plan

Status: planned, not started.

This document is the detailed execution plan for Ledger v1.4. It turns the
architecture and performance bullets in `ROADMAP.md` into measured, sequenced
work with explicit gates. v1.4 adds no user-facing features: its purpose is to
make the current application simpler, faster, more predictable, and easier to
evolve before the v2.0 browser rewrite.

The governing rule is evidence first. A plausible optimisation is not complete
until the same Release-build scenario shows a repeatable improvement without a
material regression elsewhere. An old workaround is not removed merely because
it looks unusual; its original failure mode must be retested on supported macOS
versions first.

Ledger should finish v1.4 feeling like a small, native macOS application Apple
could feasibly have shipped: responsive on the main thread, quiet when idle,
economical with files and subprocesses, and built from direct AppKit and SwiftUI
mechanisms rather than an internal performance framework of its own.

---

## Scope and constraints

In scope:

- runtime responsiveness, hangs, invalidation, CPU, memory, disk, process, and
  energy cost;
- browser item, thumbnail, preview, and metadata-loading behaviour;
- main-thread and event-handling safety;
- application and bundled-resource size;
- menu, window, split-view, and column-persistence timing;
- structural decomposition required to make a measured change safe;
- coordinated SharedUI work required by those areas;
- proportionate automation, measurement, and regression gates.

Out of scope:

- new features or visual redesigns;
- a speculative rewrite of code already scheduled to change in v2.0;
- decomposition, protocol extraction, or service layers without a concrete
  ownership or measurement benefit;
- general accessibility or SharedUI deduplication not touched by this work;
- production telemetry or external reporting;
- changing the macOS 26 deployment target;
- changing Ledger into a SwiftUI-lifecycle or document-based application;
- application sandboxing or distribution-policy changes, which belong in a
  separate security/distribution workstream;
- an open-ended “make 1,000+ files fast” project without trace evidence.

The existing cancelled large-folder performance pass remains cancelled in that
broad form. A representative large folder returns here only as a benchmark and
regression corpus. Trace-backed bottlenecks found by that gate are valid v1.4
work.

## Native performance principles

These principles govern implementation choices throughout v1.4:

1. **Keep event handling free of blocking work.** Cell configuration, layout,
   drawing, menu validation, scrolling, and keyboard handling must not perform
   synchronous filesystem access, image decode, subprocess launch, or a
   blocking wait.
2. **Load in order of user demand.** Selected and visible content comes first;
   near-visible content may be prepared next; whole-folder speculative work
   must justify its cost with measured benefit.
3. **Become idle.** Once visible and selected state has settled, Ledger should
   stop launching ExifTool, decoding previews, crawling old folders, and using
   sustained CPU unless an active user-visible operation requires it.
4. **Bound and cancel work.** Caches, request queues, background tasks, and
   retained per-file state need explicit lifetimes or limits. Folder switches,
   view detachment, window closure, and app termination must cancel stale work.
5. **Update only the active surface.** Hidden browser controllers and hosted
   SwiftUI roots must not rebuild in response to unrelated publication.
6. **Prefer native ownership.** AppKit owns the application lifecycle, menus,
   responder chain, toolbar, window, split view, collection/table views, and
   their native persistence where those APIs are sufficient.
7. **Use the smallest adequate mechanism.** Do not add a persistent helper
   process, diffable data source, Observation migration, coordinator, or custom
   persistence layer until evidence shows that the simpler mechanism is
   inadequate.

## Evidence and measurement policy

### Build and environment

Performance measurements must use a Release build. Debug builds remain useful
for warning detection but are not performance evidence.

Every report records:

- Ledger and SharedUI commits;
- Xcode path and version, Swift version, macOS version, and SDK;
- Mac model, CPU, memory, display configuration, and power state;
- benchmark corpus manifest and storage type;
- cold/warm cache state and test iteration count;
- benchmark-specific launch arguments and preference/cache roots.

The runner must select the intended Xcode explicitly through `DEVELOPER_DIR`.
Its preflight must compile SharedUI with that toolchain before a measured run,
because SDK-dependent `NSMenuItem` APIs have previously made the default
command-line toolchain unsuitable.

### Benchmark isolation and corpus safety

Media remains local and unversioned. Never record private paths or filenames.

Use two corpora:

1. **Browse corpus:** at least 1,000 representative local files described by an
   aggregate manifest of count, formats, bytes, dimensions, and storage type.
   No particular format mix is a gate unless Ledger claims to support it.
2. **Write corpus:** a runner-created disposable copy of 100 representative
   files. No metadata-write benchmark may run against originals.

The browse corpus is read-only. The write runner must create a fresh temporary
root for every iteration, place and verify a runner-specific marker inside it,
resolve every target below that marked root, and refuse writes or restores
outside it.

Benchmark preferences and caches must be isolated from normal Ledger state.
Cold-cache runs use a dedicated test cache root and never delete the real user
cache. Benchmark launch arguments disable the welcome window and Sparkle
background check so launch results do not include conditional first-run or
network activity.

### Run protocol and thresholds

- Perform at least one unmeasured warm-up before measured iterations.
- Compare medians, not the best run.
- Establish each scenario's natural variance before assigning its iteration
  count or material-regression threshold.
- Start with five measured iterations for noisy UI journeys; fewer are
  acceptable for deterministic XCTest metrics when variance supports them.
- Use the same machine, corpus, display state, power state, and toolchain for a
  before/after comparison.
- Retain an optimisation only when it produces a repeatable improvement beyond
  measured noise, removes a verified correctness defect, or satisfies a hard
  architectural gate.
- Treat no main-thread blocking I/O, no user-visible hang, bounded retained
  memory, safe cancellation, and eventual idle as hard gates rather than
  percentage targets.
- Use Apple's responsiveness guidance as a diagnostic target: investigate
  discrete main-thread intervals approaching 100 ms even when Instruments does
  not label them a hang; continuous scrolling/layout work must remain within
  the active display's frame budget.
- If a hypothesis does not improve the measured path, stop or revert it and
  record the negative result rather than expanding its scope.

### Baseline scenarios

Record at least:

- process launch to static menu readiness and first usable browser window;
- folder selection to first stable browser paint;
- first visible thumbnail and all visible thumbnails hydrated;
- visible filesystem attributes and metadata subtitle hydration;
- cold and warm folder reopen;
- List, Icon, and Gallery/Filmstrip switching;
- Name and metadata-backed sorting;
- sustained scrolling and rapid keyboard selection with inspector visible;
- sidebar and inspector collapse/expand, live resize, and relaunch restoration;
- metadata apply and restore for 1, 10, and 100 files;
- ExifTool read/write subprocess counts and total durations;
- time to quiescence after folder load, folder switch, and window closure;
- idle and peak resident memory, sustained CPU, Energy Impact, idle wakeups,
  disk activity, and hangs;
- retained metadata/preview counts and memory after navigating 20–50 folders;
- memory- and disk-cache size before and after the run;
- executable, ExifTool, resources, and total app-bundle size.

Run the appropriate subset against an internal local volume, a representative
external/removable volume, iCloud placeholders without implicit materialisation,
and missing, disconnected, or permission-denied locations.

## Phase 0 — Thin measurement harness and baseline

Complete this phase before changing performance-sensitive production code, but
do not turn it into a bespoke performance platform.

### 0.1 Stable instrumentation

Add `OSSignposter` intervals around a small set of stable journeys:

- application launch, static menu readiness, and first usable window;
- folder enumeration, initial item publication, and first stable paint;
- visible-thumbnail and visible-attribute hydration;
- selected/visible metadata loading and any remaining folder prefetch;
- browser view-mode and sort transitions;
- ExifTool read, apply, reload, restore, and subprocess lifetime;
- transition to quiescence after a foreground journey.

Use a stable subsystem/category and static interval names. Give concurrently
possible operations distinct signpost IDs, retain the returned interval state,
and guarantee exactly one matching end, normally with `defer`. Capture the
`os_signposts` instrument so mismatched or missing intervals are visible.

### 0.2 Proportionate runner

Create an on-demand local wrapper under `scripts/performance/` that initially:

- validates the requested Xcode, SharedUI build, and corpus locations;
- builds Ledger in Release configuration;
- supplies isolated preferences/cache roots and benchmark launch arguments;
- runs warm-up and measured iterations;
- captures named Instruments templates where command-line capture is reliable;
- records wall time, signposts, subprocess count, memory, CPU, Energy Impact or
  CPU/I/O proxies, idle wakeups, disk use, cache counts, and app size;
- retains raw traces in ignored output and produces a sanitised comparison
  table suitable for committing.

A shell wrapper, focused XCTest metrics, raw trace files, and a reviewed
Markdown table are sufficient initially. Add general JSON reporting or
automated trace parsing only after repeated use shows that it pays for itself.
Set XCTest baselines and maximum standard deviation only after baseline
variance is understood; profile performance-test failures directly in
Instruments.

### 0.3 Deterministic UI driving

Add accessibility identifiers and a small UI-test target for only three to five
stable journeys at first. Candidates are configured-folder selection, browser
mode switching, sorting, scrolling/selection, pane toggles, and a disposable
metadata apply/restore flow.

Use native XCTest metrics where they match the work. Do not ask UI automation
to judge subjective animation quality or a one-frame flash; its role is to
reproduce the same action and mark timing boundaries.

### 0.4 Baseline and warning inventory

Save the sanitised baseline before Phase 1. Capture focused traces with Time
Profiler and File Activity for launch, cell configuration, scrolling, metadata
loading, writes, cache maintenance, and folder switching. File Activity review
must distinguish logical filesystem calls from physical bytes/latency and note
create/delete churn. Use Hangs and Animation Hitches for interaction journeys,
Allocations/Leaks for retained-state scenarios, and SwiftUI Instruments only
for hosted SwiftUI surfaces.

On macOS, use Activity Monitor Energy Impact, Xcode CPU/disk/network gauges,
idle-wakeup/timer inspection, and CPU/I/O measurements rather than making the
iPhone/iPad Power Profiler an automated requirement.

In a Debug smoke run, attempt to reproduce the old “Publishing changes from
within view updates is not allowed” warning from `ROADMAPOLD.MD`. If it cannot
be reproduced after the AppKit sidebar migration, mark it superseded with the
exact smoke path used. `CMPhoto`/`IOSurface` messages remain observation-only
unless correlated with blank images, repeated decode failure, a hang, or crash.

Exit gate:

- the harness repeats chosen journeys without manual timing;
- reports contain complete environment/corpus metadata;
- write data and normal user state are protected by hard preflight checks;
- each primary metric has a recorded noise range;
- current main-thread I/O, hang, background-work, and memory-growth findings
  are classified before implementation begins.

## Phase 1 — Main-thread responsiveness and render scope

This is the first production-code phase because it addresses work capable of
blocking direct interaction.

### 1.1 Remove synchronous thumbnail disk work from UI paths

`ThumbnailService.cachedImage` currently falls back from `NSCache` to
synchronous file existence/staleness checks and `NSImage(contentsOf:)` decode.
That API is used by synchronously configured browser and preview surfaces.

Profile the existing path, then make synchronous lookup memory-only. Move disk
lookup, source-mtime validation, and decode behind the asynchronous thumbnail
broker. Preserve stable first paint through visible-item prewarm,
already-published low-resolution images, or a native placeholder rather than
blocking cell configuration to avoid a one-frame fallback icon.

Test cold/warm cache, corrupt or missing cache entries, internal/external
volumes, rapid scrolling, folder switching, memory pressure, and cancellation.

Exit gate: browser cell configuration, drawing, scrolling, selection, and
preview-root updates perform no synchronous filesystem access or image decode.

### 1.2 Update only the active browser surface

Audit `BrowserContainerViewController` subscriptions and render routing before
changing observation technology. The container currently observes complete
browser, metadata, selection, and pending-operation collections and sends each
coalesced render to Icon, List, and Filmstrip controllers. Filmstrip also
replaces its `LargePreviewPane` root before checking whether Gallery is active.

- Route item/render updates only to the active controller.
- Do not recreate or update hidden hosted SwiftUI roots.
- Separate overlay and path-bar state from browser-content invalidation.
- Remove redundant observation of source and derived collections where one
  publication already implies the other.
- Prefer a small revision or changed-URL set over a complete high-churn
  dictionary when traces show the dictionary publication is material.
- Add temporary counters/signposts for container renders, inactive-controller
  updates, visible-cell configuration, and hosting-root replacement.
- Preserve selection, responder-chain behaviour, pending edits, and immediate
  correctness when switching modes.

Exit gate: an update relevant to one browser surface causes no render work in
the hidden surfaces, high-churn metadata no longer rebuilds unrelated hosted
content, and counters confirm the reduction without stale UI.

### 1.3 Hangs and event-loop gate

Use Hangs, Time Profiler, File Activity, and Animation Hitches on scrolling,
keyboard selection, mode changes, pane animation, live resize, metadata writes,
and menu opening. Inspect every synchronous `Process`, file-read, image-decode,
layout, and wait stack found on the main thread. Fix verified cases rather than
relying only on aggregate launch or scrolling numbers; fix hangs before hitches.

Exit gate: defined journeys show no unexplained main-thread blocking I/O, long
event-handling interval, or repeatable visible hitch.

### 1.4 Lifecycle and local structural decomposition

Establish one lifecycle convention for AppKit controllers and SwiftUI/AppKit
bridges that own observers, event monitors, Combine subscriptions, delegates,
or tasks. Installation and teardown must be symmetric; lifetime-scoped state
may instead be released in `deinit`. Clear view delegates and other borrowed
references during bridge dismantling where required.

Add a detach/reappear smoke path covering browser publication, focus requests,
mode switching, split callbacks, toolbar/menu refresh, and thumbnail
cancellation. Every callback must resume exactly once: no missing subscription
after reappearance and no duplicate observer.

Split `MainContentView.swift` only as Phase 1 and Phase 4 changes require, using
extensions/files organised by existing AppKit responsibility. Continue
decomposing `AppModel` only at natural boundaries encountered by measured work.
Do not add protocols, coordinators, forwarding types, or thin files just to
reduce line count. Source movement is not a runtime optimisation.

## Phase 2 — Demand-driven metadata, previews, and quiescence

### 2.1 Replace whole-folder eagerness with a demand order

The current deferred prefetch begins shortly after folder selection, reads the
entire folder in small batches, and publishes an increasingly large
`metadataByFile` dictionary after each batch. External locations reduce the
batch to one file, increasing subprocess fan-out.

Measure and implement this demand order:

1. metadata for the selected file or selection;
2. metadata needed by visible List columns or Icon subtitles;
3. visible and near-visible browser items;
4. remaining folder metadata only when a current sort, filter, export, or other
   visible requirement needs it.

Base batch sizes on measured ExifTool startup and storage behaviour, not a
universal constant. Publish useful deltas without repeatedly comparing or
copying the complete session dictionary where practical. Track read subprocess
count and duration separately from writes.

A persistent ExifTool process is an evidence-gated fallback only if demand
shaping and batched reads remain inadequate; its lifecycle and failure
complexity must be justified before adoption.

### 2.2 Bound speculative preview work

Review initial thumbnail warmup, inspector-neighbor preload, deferred preview
preload, and warming for the folder the user has just left. Keep each only if it
improves a measured return/navigation journey without delaying foreground work
or producing significant CPU, wakeup, or disk cost.

Old-folder work must not compete with the selected folder. Closing/detaching the
window or switching folders cancels obsolete metadata, thumbnail, preview, and
cloud-state work. Never materialise an iCloud placeholder for speculative cache
warming.

### 2.3 Idle and cancellation gate

Record time to quiescence after initial display, folder switch, mode switch,
selection sweep, and window closure. At quiescence:

- no obsolete ExifTool processes start;
- no old-folder thumbnail or preview decode remains queued;
- no repeated metadata publication or layout continues;
- CPU, disk, wakeups, and Energy Impact return to the measured idle band;
- disconnecting a removable volume or losing access ends affected work safely
  and leaves a coherent UI.

Exit gate: selected and visible data wins every priority contest, obsolete work
is cancelled, and Ledger reliably becomes idle after each foreground journey.

## Phase 3 — Bounded data, disk, process, and binary cost

### 3.1 Bound retained metadata and preview state

`metadataByFile` is preserved across folder switches while the inspector
preview cache already has an entry bound. Measure retained objects and resident
memory after navigating 20–50 folders and after memory pressure.

Define a per-folder lifetime, LRU, or measured cost budget for metadata
snapshots and associated console/history state. Protect the current selection,
active folder, pending edits, undo/restore requirements, and in-flight
operations. Verify evicted metadata reloads correctly and resident memory
reaches a plateau rather than growing with every folder visited.

### 3.2 Batch ExifTool metadata writes

Replace the one-process-per-file write loop with a batched mechanism supported
by ExifTool. Preserve exact arguments, per-file success/failure attribution,
backup creation/retention/restore, cancellation, timeout, post-write reload, and
user-facing result counts.

Test full success, middle and multiple failures, locked files, timeout,
cancellation, backups disabled, and restore. Measure 1, 10, and 100 files,
recording subprocess count, CPU, disk writes, and wall time.

Exit gate: the 100-file path uses a bounded number of launches, preserves
result fidelity, and improves measured duration without moving single-file
performance outside its noise band.

### 3.3 Bound the thumbnail disk cache

Design the size/age policy using the baseline corpus rather than choosing an
arbitrary cap. It must:

- enforce a documented upper bound and trim target;
- evict oldest eligible entries first;
- scan/delete at utility priority outside launch, cell configuration, scrolling,
  and decode paths;
- rate-limit maintenance rather than scan on every request;
- preserve source-mtime validation;
- tolerate missing, corrupt, or concurrently removed files;
- coexist with `NSCache` memory-pressure eviction.

Unit-test selection/deletion with a temporary cache. Benchmark over-limit
maintenance and confirm normal warm-cache browsing remains unchanged.

### 3.4 Remove confirmed redundancy and reduce shipping payload

Remove the confirmed dead EOS-1V shooting-row model/loaders, unused embedded
EOS lens mapping, and CSV parser duplicated by `CSVSupport`. Expand only where
reference searches and tests prove a symbol unused or duplicated. Treat this as
maintainability/payload hygiene, not a claimed runtime speed-up.

Audit ExifTool tests/demo modules and prune only paths proven unnecessary at
runtime. Exercise metadata read/write, import, CSV export, and restore from the
pruned built app. Re-export `EOS1VBody.png` near its displayed requirements,
retaining appropriate display-scale representations and visible quality. Keep
Release symbol stripping and dSYM generation.

Exit gate: record before/after executable, ExifTool, resource, and total app
sizes and complete every ExifTool-backed smoke path from the built bundle.

## Phase 4 — Native AppKit menu, window, and persistence ownership

### 4.1 Own the static menu before hosted UI

Follow `menu-bar-architecture-audit-2026-08.md`. Replace launch-time and
menu-tracking reinjection with a dedicated AppKit menu builder owned by the
application delegate:

- create the complete static menu hierarchy and key equivalents before any
  `NSHostingController`/`NSHostingView` or first window is constructed;
- route actions through the responder chain;
- use `validateMenuItem` for enabled/check state;
- use `menuNeedsUpdate(_:)` for normal dynamic updates immediately before
  display; if population is proven expensive, use AppKit's incremental menu
  delegate APIs rather than blocking open;
- update only menu properties that changed and keep pasteboard, filesystem,
  ExifTool, and other IPC off menu construction/validation paths.

The production result must not retain a throwaway hosting view, timing-based
SwiftUI mutation trigger, or `NSMenu.didBeginTrackingNotification` reinjection
without a new evidence-backed justification. Verify that constructing hosted
SwiftUI panes/sheets cannot replace or strip Ledger's menu structure.

### 4.2 Prefer AppKit persistence

Implement `window-list-resize-diagnosis-2026-07.md` as one coordinated effort
covering window frame, split dividers, and table columns. “One ownership model”
means removing overlap, not adding another coordinator.

- Prefer stable, unique AppKit frame, split, and column autosave identifiers.
- Check autosave registration success and remove duplicate manual saves.
- Persist custom state only where AppKit cannot represent the product rule.
- Never persist programmatic fit/restore as user drag intent.
- Apply one-time initial fitting only after restored window/split widths settle.
- One completed user drag produces one durable update, not writes throughout
  live resize.
- Visible columns fit the viewport unless summed minimum widths require
  horizontal overflow.
- Define deterministic fallback for invalid, off-screen, or legacy state.

Test fresh/existing preferences, same- and cross-display relaunch, monitor
removal, resolution change, move/resize, divider drag, column reorder/resize,
and necessary horizontal overflow.

### 4.3 Coordinated SharedUI audit

SharedUI owns its chrome-workaround inventory, sidebar inactive-window label,
and sidebar-cell rebuild. Test Ledger and other consumers together, but keep
the detailed backlog in SharedUI.

For every workaround: disable it on macOS 27, reproduce the original path, then
delete, replace with a native API, or retain it with the OS/build where last
verified necessary. Reconfirm retained behaviour on macOS 26.

Re-evaluate `WorkflowInlineRadioGroup` only if touched; use native SwiftUI radio
controls only when disabled options and layout remain correct.

Exit gate: the menu is correct from launch without reinjection, geometry has a
single documented native-first owner with no feedback loop, and every reviewed
workaround has an evidence-backed disposition.

## Phase 5 — Evidence-gated browser and Observation refinements

This phase contains optional optimisations, not migration targets.

### 5.1 Measure collection reload cost

Icon and Filmstrip retain full reloads principally for item identity/count and
all-cache invalidation; per-URL invalidations and List updates are already more
targeted. After Phases 1–3, record full/targeted reload and visible-cell
configuration counts by trigger for folder changes, sorts, filters, hydration,
and thumbnail invalidation.

- Keep full reloads where identity changes and traces show no material problem.
- Never broaden existing targeted reload scope.
- Use narrower reloads or diffable snapshots only for proven costly paths.
- Do not assume diffable is intrinsically faster: animated snapshot application
  computes a linear diff, so measure snapshot creation/application separately.
- Use stable, lightweight identifiers and a consistent queue if diffing away
  from the main queue.
- Preserve selection, primary item, scroll anchor, focus/first responder,
  accessibility, pending edits, and Quick Look source frames.

### 5.2 Optional Observation pilot

Observation migration is a hypothesis, not a completion requirement. The main
browser is AppKit-driven, and changing `@Published` to `@Observable` does not by
itself narrow Combine subscriptions or whole-dictionary updates.

Open a bounded pilot only if SwiftUI Instruments or invalidation counters still
show a material hosted-SwiftUI problem after render routing and publication
scope are fixed. Record invalidations, CPU, responsiveness, memory, warnings,
and test behaviour before/after. Continue only for repeatable benefit and clearer
ownership; stop when benefit is within noise or AppKit bridging becomes more
complex.

Complete Combine removal is not a goal where publishers remain the correct
AppKit bridge. Async/await is not a substitute for every state observation.

### 5.3 Browser regression matrix

Automate the stable subset of cold/warm relaunch, cached/uncached switching, all
browser modes, sorts, subtitles, selection sweeps, metadata apply, thumbnail
invalidation, cancellation, memory pressure, and controller detach/reappear.
Manually verify no fallback-icon flash, stale subtitle, missing cloud badge,
implicit cloud download, selection jump, lost focus, or duplicate callback.

Exit gate: all browser surfaces converge on correct data, no trace-backed
large-folder bottleneck remains unclassified, optional migrations have explicit
accept/reject evidence, and v2.0-exposed work has not been over-engineered.

## Phase 6 — Final verification and close-out

Repeat Phase 0 on the same machine, corpora, toolchain, benchmark state, and
storage types. Produce a final table containing baseline/final medians and
variance for every primary metric, plus process/cache/app sizes and test status.

### Automated gate

- Ledger and SharedUI builds/tests with the pinned toolchain;
- launch, signpost, and deterministic UI metrics;
- main-thread I/O, responsiveness, and hitch traces for critical journeys;
- ExifTool read/write batching, partial-failure, cancellation, and timeout tests;
- backup/apply/restore and pruned-bundle integration tests;
- metadata/thumbnail cache bounds, pruning, pressure, stale, and corruption tests;
- browser cold/warm/load/switch/invalidation/reappearance scenarios;
- idle/quiescence and stale-work cancellation scenarios;
- window/menu/column persistence scenarios where UI automation is reliable;
- binary/resource size and warning reports;
- targeted tests for accepted Observation or diffable-data-source slices.

### Manual gate

- one-frame flashes, animation quality, menu timing, and native AppKit feel;
- keyboard navigation, responder chain, standard shortcuts, and menu ordering;
- Reduce Motion and accessibility behaviour on touched surfaces;
- macOS 26 and 27 chrome/window behaviour;
- external-volume disconnect and iCloud-placeholder behaviour;
- real EOS-1V camera and ES-E1 cable smoke where touched code could interact;
- any framework log correlated with a visible failure during automation.

### Documentation close-out

- Update `ROADMAP.md`, `CHANGELOG.md`, and the release checklist as work lands.
- Record rejected and retained hypotheses as deliberately as completed work.
- Mark old B22/B23/R10 items superseded, observation-only, or covered by a named
  v1.4 gate; do not leave duplicate ambiguous backlog entries.
- Keep sanitised baseline and final reports with the v1.4 release evidence.

v1.4 is complete when the final comparison is recorded, no material unexplained
regression remains, the main-thread/idle/bounded-resource gates pass, every
roadmap workstream has an explicit disposition, and manual QA is limited to
genuinely perceptual, cross-operating-system, storage, or hardware-dependent
behaviour.
