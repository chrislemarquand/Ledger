Five real things were discovered only by actually running this against the
built app (none guessable from source):
1. **`LedgerUITests-Runner` is sandboxed** with read-only access to all of
   `/` but write access only inside its own container (confirmed via
   `codesign -d --entitlements -`). This blocks the obvious approach of
   having the test process copy fixture images to a shared writable temp
   location — `FileManager.default.temporaryDirectory` is invisible to the
   separately-launched, unsandboxed Ledger process ("Folder Unavailable"),
   and a hardcoded `/tmp` path is flatly denied to the sandboxed test host
   ("Operation not permitted"). Fix for the read-only journeys implemented
   here: point `-openFolderPath` directly at the test bundle's own Resources
   folder (`Bundle(for: Self.self).resourceURL!`) — no copying, since the
   sandboxed host can read anywhere. A write-capable journey (metadata
   apply/restore) has no equivalent easy fix and is deferred.
2. Per (1), **HOME isolation isn't achievable for UI tests** the way
   `scripts/performance/run_benchmarks.sh` does it for direct-executable
   launches — same container-isolation blocks it. UI tests run against your
   real, developer-machine Ledger preferences. Consequence: **running these
   tests may change your last-used view mode/sort order in Ledger.** Nothing
   about file contents, metadata, or data is touched.
3. The view-mode segment's real accessibility label is **"Icon"** (singular)
   — the source's `labels: ["Icons", "List", "Gallery"]` array in
   `MainContentView.swift` does not match what AppKit actually exposes.
   Caught by dumping the real accessibility hierarchy
   (`app.debugDescription`) rather than guessing from source, which is the
   general lesson here: write one exploratory dump test against a live
   launch before authoring real locators for any new UI-test journey.
4. The Sort toolbar item is an `XCUIElement.ElementType.menuButton`, not
   `.button` — `app.buttons["Sort"]` silently never matches.
5. **The Sparkle background-update check was not actually suppressed** —
   the update window appeared on every launch despite seeding
   `SUEnableAutomaticChecks` via `defaults write` (Phase 0.2's approach).
   Replaced with a real launch argument, `-disableSparkleAutoupdate`,
   gating the call to `updateService?.performBackgroundCheck()` directly in
   `LedgerApp.swift` — reliable because it's in code, not hoping Sparkle
   honors a preference. Both `run_benchmarks.sh` and `LedgerUITests.swift`
   now pass this flag. If you ever see the Sparkle window during a
   benchmark/test run again, this is the first place to check.

**Bugs found and fixed while validating 0.2 against a real run — all three
would have made the runner silently hang or misreport, so treat this list as
required reading before trusting output from a *new* scenario added later:**
1. `log stream` excludes signpost events by default even at `--level info`
   — needs an explicit `--signpost` flag. Verified the real ndjson field
   shape (`signpostName`, `signpostType: begin/event/end`; `eventMessage` is
   always empty for signposts) via a manual probe capture before trusting
   the parser.
2. `pid=$(some_function_that_backgrounds_a_process)` blocks until that
   background process *exits* — it inherits the command substitution's
   stdout pipe, so `$(...)` doesn't return on EOF until every holder of that
   pipe's write end closes it, including the long-lived GUI process. Fixed
   by redirecting the launched app's stdout/stderr to `/dev/null` inside
   `run_isolated_launch`. This is a general trap for any future scenario
   function that backgrounds+captures-PID in one call — always redirect the
   backgrounded command's own stdout/stderr away from the enclosing
   function's stdout.
3. A bare `kill "$pid"; wait "$pid"` hung indefinitely in this machine's
   system bash (3.2) when `$pid` came from a command-substitution subshell.
   Fixed with a bounded poll-then-SIGKILL helper (`terminate_process`),
   mirroring `scripts/release/release_check.sh`'s existing `run_with_timeout`
   pattern rather than inventing a new one.

Also: macOS ships bash 3.2, not bash 4.3+ — `local -n` namerefs don't exist.
`median()` takes array elements as positional args instead.

### Phase 1.1 detail

`ThumbnailService.cachedImage(for:minRenderedSide:)` fell back from the
memory `NSCache` to a synchronous `readDiskCache` call (`FileManager`
existence + mtime stat, then `NSImage(contentsOf:)` decode) on a memory-cache
miss — real disk I/O and image decode running inline on whatever thread
called it.

Used a fork to classify all 19 call sites first rather than guess scope:
13 were genuine synchronous UI hot paths (List/Icon/Filmstrip cell
configuration via `NSCollectionViewDataSource`/table cell-config methods,
plus the aspect-ratio helpers and per-cell `requestThumbnail` guard checks
those call into; and the inspector/large-preview chain reached synchronously
from `collectionView(_:didSelectItemsAt:)` via `loadInspectorPreview`), 2
were `NSCollectionViewPrefetching` callbacks (main-thread-dispatched by
AppKit but for off-screen rows, lower priority), and 6 were already safely
inside async `Task` contexts or explicit background-warm functions.

Fix: stripped the disk fallback out of `cachedImage` itself — it's now
memory-cache-only — rather than rewriting all 13 hot-path call sites
individually. Every one of them already had an async `request()` fallback
wired up for the "not cached" case (that's the existing two-tier
check-then-request pattern used throughout the browser views), so a
memory-cache miss now correctly falls through to the path that was already
there instead of doing its own disk read. `readDiskCache` remains reachable
from the async `generate()` path (inside the broker), so disk-cache hits are
still honored — just asynchronously.

**This is a compile-time-verifiable guarantee, not an empirical one**:
`readDiskCache` is a `private static func` in `ThumbnailService.swift`, and
grepping the file confirms its only two callers are the now-fixed
`cachedImage` (removed) and `generate` (already async, inside
`broker.request`). No other synchronous disk I/O (`NSImage(contentsOf:`,
`FileManager.default.fileExists`, `Data(contentsOf:`, etc.) exists anywhere
in the four hot-path files (`BrowserIconView.swift`, `BrowserListView.swift`,
`BrowserFilmstripViewController.swift`, `AppModel+MetadataPipeline.swift`) —
confirmed by grep, not just reasoning about this one function.

Accepted trade-off (the plan's own framing): a thumbnail that's warm on disk
but was evicted from the in-memory `NSCache` (app relaunch, memory pressure)
now shows a placeholder/fallback icon for one more render pass instead of
appearing synchronously, rather than blocking cell configuration to avoid
that frame.

Full regression suite re-confirmed green (208 tests, 0 failures) after the
change. Not yet done: the plan's fuller manual test matrix (cold/warm cache,
corrupt cache entries, internal/external volumes, memory pressure,
cancellation) — the automated tests don't specifically exercise disk-cache
eviction/corruption scenarios. A `--trace` Time Profiler capture during the
`folder-load` benchmark scenario exists (`scripts/performance/output/raw/.../*.trace`,
gitignored) as manual-review evidence if wanted, though the structural
grep-based guarantee above is stronger than what a single profiling run
could show empirically.

### Phase 1.2 detail

`BrowserContainerViewController.render()` called `.update(model:items:)` on
all three of `iconController`/`listController`/`filmstripController`
unconditionally on every render, regardless of which one `model.browserViewMode`
actually made visible — confirmed these are the *only* path driving those
controllers (grepped for independent Combine subscriptions inside
`BrowserIconView.swift`/`BrowserListView.swift`/`BrowserFilmstripViewController.swift`;
none exist, everything comes through the container). This exactly matched
the plan's own cited example: Filmstrip's `update()` set
`previewHostingView.rootView = LargePreviewPane(model: model)` (a hosted
SwiftUI root) at the very top, before its own guard checking whether Gallery
was even the active mode — so that hosted root was being replaced on every
render while Gallery was hidden.

Fix: `render()` now `switch`es on `model.browserViewMode` and calls
`.update()` on only the matching controller. Because `applyBrowserModeIfNeeded`
(which swaps view visibility) runs earlier in the same `render()` call,
`model.browserViewMode` is already current by the time the switch runs — a
mode switch's newly-active controller gets a correct, immediate update on
the very same render pass, no staleness window. This resolves the Filmstrip
hosting-root case as a side effect, not a separate fix: with the switch in
place, `filmstripController.update()` (and therefore the `previewHostingView.rootView`
assignment) simply isn't called at all while Gallery isn't active.

Like Phase 1.1, the "no render work in hidden surfaces" guarantee here is
structural (a `switch` can only take one branch) rather than something
proven only by a counter. Verified via the full regression suite, including
`LedgerUITests.testBrowserViewModeSwitching`, which exercises exactly this
code path (Icon→List→Gallery→Icon) and confirms no staleness was introduced.

**Explicitly not done, pending trace evidence per the plan's own
instruction** ("Prefer a small revision or changed-URL set over a complete
high-churn dictionary **when traces show the dictionary publication is
material**"):
- Removing redundant observation between `$browserItems` and
  `$filteredBrowserItems` in `installRenderObservers()` — both are observed
  separately, but a `$browserItems` change likely always implies a
  `$filteredBrowserItems` change too. Combine's synchronous re-entrant
  publishing plus the existing `MainActorCoalescer` probably already
  collapses these into one actual `render()` call in practice, meaning the
  fix might not be worth the complexity — not measured either way yet.
- Replacing `$metadataByFile`'s full-dictionary publication with a smaller
  revision/changed-URL set. No trace evidence yet showing this dictionary's
  publication is actually material to render cost; doing this without that
  evidence would be exactly the kind of unproven structural change the plan
  warns against.
- Temporary render/inactive-update/hosting-root-replacement counters the
  plan suggests adding — skipped because the fix already makes the thing
  they'd count structurally impossible (same reasoning as Phase 1.1's
  compile-time-verifiable framing), so there's nothing left to counter-verify
  empirically. Revisit if a future profiling pass wants call-frequency data
  for a different reason (e.g. investigating render() firing too often in
  general, independent of which controller it targets).

### Phase 1.3 detail: hangs/hitches capture workflow

**What's automatable vs. not, decided empirically this round:**
- Trace *capture* (Time Profiler; Animation Hitches is the other directly
  relevant template — there's no standalone "Hangs" template, hang
  detection lives inside Time Profiler's `potential-hangs`/`hang-risks`
  tables) is fully automatable via `xctrace record --attach <pid>`.
- Driving the interaction itself via `osascript`/System Events proved too
  flaky to rely on: AX property reads (`title of radio button ...`)
  intermittently returned real values ("Icon") and then `missing value` on
  the next query with no code change, and the window's title changes
  dynamically during folder load in a way that broke cached AppleScript
  object references mid-script. Not worth fighting — the user does the
  interaction manually instead, which is both more reliable and exercises
  the real thing (a script clicking a button isn't quite the same signal
  as a human actually using the app).
- **Live resize is explicitly not worth automating even if it could be
  forced via AppleScript's `set bounds`** — that would be a discrete
  frame-set, not a continuous drag, and wouldn't reproduce the actual
  bug class (repeated layout passes *during* a drag).
- Metadata writes remain blocked by Phase 0.3's sandboxed-write-visibility
  finding (no location both a test harness and Ledger can write to without
  real design work).

**Working hybrid workflow** (repeatable for the remaining journeys):
1. Launch Ledger directly (not through XCUITest) with the browse corpus
   open, same isolated-HOME approach as `run_benchmarks.sh`.
2. Poll `osascript -e 'tell application "System Events" to tell process
   "Ledger" to return name of window 1'` until the title stops showing
   "Loading" — reading a property this way was reliable even though
   clicking wasn't.
3. Start `xcrun xctrace record --template 'Time Profiler' --attach <pid>
   --time-limit Ns --output foo.trace --no-prompt` in the background, and
   in the same turn ask the user to perform the interaction sequence live
   — the ask needs to land in the same message as starting the capture so
   the timing lines up.
4. `xcrun xctrace export --input foo.trace --xpath '/trace-toc/run[@number="1"]/data/table[@schema="potential-hangs"]'`
   gives hang start-time/duration/thread directly as XML — genuinely
   useful without opening Instruments. Cross-reference a hang's timestamp
   against the `time-profile` table's `sample-time` (same query pattern,
   filtered to the `<thread ref="N"/>` matching Main Thread — find N via
   `grep -o '<thread id="[0-9]*"[^/]*fmt="[^"]*Main Thread[^"]*"'`) to pull
   the actual call stack during the hang window.

**First real capture (2026-08-31), partial interaction coverage** — the
user got through scrolling and part of the mode-switching/selection list
before time ran out, not the full sequence (pane toggle, menu open, and
possibly live resize were attempted but not confirmed complete). Found:
two genuine main-thread "Microhang" entries in `potential-hangs`, ~300ms
each, ~900ms apart, around the 45–47s mark. Pulled the call stacks for
that window: dominated by generic AppKit/SwiftUI window-interaction
machinery (`-[NSWindow(NSEventRouting) _reallySendEvent:...]`,
`-[NSView _windowChangedKeyState]`, `AG::Graph::propagate_dirty`/`ViewGraph.invalidateTransform()`)
— consistent with a window resize or titlebar drag, not app code. Only
**one** frame in the entire hang window's stacks mentioned Ledger code
(`BrowserContainerViewController`, incidental). **Read as: this specific
hang is AppKit/SwiftUI's own window-interaction cost, not a Ledger defect
in the areas Phase 1 targets** — matches the plan's own framing of live-resize
cost as a largely system-level category. No code change indicated from
this data alone.

**Second capture (2026-08-31), keyboard selection + pane toggle + menu
opening + more window resizing** — this time using a generous 180s
safety-net `--time-limit` and ending the recording early via `SIGINT` (same
as Ctrl-C) once the user confirmed they were done, rather than guessing a
fixed duration up front. Result: **zero rows in `potential-hangs`** — clean.
Confirmed the capture actually held real data (21,828 time-profile samples,
not an empty/failed run) before trusting the zero-hangs read. Notably, this
pass also included window resizing and did *not* reproduce the first
capture's hang, reinforcing that the earlier microhang wasn't a repeatable
Ledger-caused defect. Trace retained:
`scripts/performance/output/interaction-traces/interaction-20260831-203911-keyboard-pane-menu.trace`
(gitignored, 39MB).

**Exit gate assessment**: across both captures (scrolling, mode-switching,
keyboard selection, pane toggle, menu opening, window resize), no
unexplained or repeatable main-thread hang was found — the one instance
seen was traced to generic AppKit/SwiftUI window-interaction machinery and
didn't recur under similar conditions. Treating 1.3 as met for the journeys
that could be tested. Metadata writes remain the one journey this
workflow can't reach (same sandboxed-write-visibility wall as Phase 0.3's
deferred metadata apply/restore UI test) — revisit together if that
blocker ever gets solved.

### Phase 1.4 detail

Used a fork to audit every Combine subscription, `NotificationCenter`
observer, `NSEvent` monitor, delegate assignment, and long-running `Task`
across the browser controllers, `NativeThreePaneSplitViewController`,
`EOS1VDeviceMonitor`, and the secondary windows (Settings, ExifTool
console) for install/teardown symmetry — read-only, no changes, before
touching anything.

**Good news the audit surfaced**: the codebase already follows a consistent
lifecycle convention almost everywhere. `BrowserIconViewController`,
`BrowserListViewController`, `BrowserFilmstripViewController`, and
`NativeThreePaneSplitViewController` all correctly pair `viewDidLoad`
installs with `viewWillDisappear` teardown (matching
`BrowserContainerViewController`'s existing pattern from before this
audit). `AppModel`'s many stored `Task` properties are all consistently
cancelled-and-reassigned at every call site (the correct "coalescing
task" pattern, not a leak) — no `deinit`-based sweep needed since
`AppModel` is created once and never deallocated for the process's life.
Settings/ExifTool console windows are created once, kept alive, and don't
install anything of their own to tear down.

**One real, confirmed gap, now fixed**: `EOS1VDeviceViewController` and
its file-private sibling `EOS1VConnectViewController`
(`Sources/Ledger/EOS1V/EOS1VDeviceViewController.swift`) both installed a
Combine `sink` on `session.objectWillChange` in `viewDidLoad`, into a
`Set<AnyCancellable>`, with **no `viewWillDisappear` override at all** —
the one place in the audited surface that broke the convention every
other controller follows. Currently low real-world risk (the `session`
object they subscribe to is itself created once and never deallocated,
same as `AppModel`), but a genuine inconsistency worth fixing for its own
sake — "establish *one* lifecycle convention" means this file should
follow it too, not that it's safe to skip because nothing has been hurt by
it yet. Added the matching `viewWillDisappear` override to both classes.

**Explicitly not fixed, and why**: `MainContentView.swift`'s menu-injection
methods (`injectFileMenuIfNeeded` etc.) set `submenu.delegate = self` on
`NSMenu` objects borrowed from `NSApp.mainMenu`, and never explicitly
reset that delegate on teardown. The audit flagged this as
reachability-uncertain rather than a bug: `NSMenu.delegate` is a `weak`
AppKit property (auto-nils on deallocation, no dangling-pointer risk), and
the surrounding code already documents and tolerates SwiftUI occasionally
rebuilding these `NSMenu` objects and invalidating the weak references
(re-registering the delegate on `NSMenu.didBeginTrackingNotification`).
The real uncertainty is untestable in practice: this app only ever creates
one `NativeThreePaneSplitViewController` for its whole life, so there's no
way to exercise what happens if a second instance ever contended for the
same main-menu submenus. Not fixing a theoretical problem with no evidence
path, consistent with the plan's own "don't add structure without a
concrete benefit" instruction elsewhere.

**"Add a detach/reappear smoke path"**: the audit found no code path in
the app that detaches/reappears the main window or its browser
controllers independent of quitting — this is a single-window app with no
"close without quit" flow in the reviewed files. A smoke test for a
scenario that structurally can't happen wouldn't test anything real; the
plan's underlying concern (no missing subscription after reappearance, no
duplicate observer) is covered by the fact that every install site
already guards against being called twice (e.g.
`GallerySelectionAppearanceObserver.start()`'s `if selectionAppearanceObserver == nil`
guard, `installKeyMonitorIfNeeded()`'s guard) — verified by the audit, not
newly added.

**"Split MainContentView.swift"**: deliberately not done. The plan's own
instruction is to split it "only as Phase 1 and Phase 4 changes require"
— none of the Phase 1.1–1.4 work needed to touch its structure. Splitting
it now would be source movement with no measured benefit, which the plan
explicitly calls out as not a runtime optimization.

`EOS1VDeviceViewController`/`EOS1VConnectViewController` fix.

### Incident: the benchmark harness was never actually isolated

Verifying 2.1's subprocess-count claim surfaced a serious, unrelated
problem in the Phase 0.2 benchmark infrastructure itself, discovered by
accident: a real user preference (Icon subtitle set to a metadata field,
"Shutter Speed") leaked into what was assumed to be a fresh, isolated
benchmark run.

**Root cause**: `run_benchmarks.sh`'s `run_isolated_launch` redirected
`HOME` for the launched process and used `defaults write` to seed
preferences, on the assumption (stated explicitly in Phase 0.2's own
writeup) that this fully isolates `~/Library/Preferences`,
`~/Library/Caches`, and `~/Library/Application Support`. **This was never
true.** `NSHomeDirectory()` and `cfprefsd`-backed `UserDefaults`/`defaults`
both resolve the home directory via the real system passwd record
(`getpwuid`), not the `HOME` environment variable, for an unsandboxed
process on this platform. Confirmed empirically: no plist or cache file
was ever created under any of the "isolated" home directories used this
entire session — every launch since Phase 0.2 read and wrote the real
`~/Library/Preferences/com.chrislemarquand.Ledger.plist`, the real
`~/Library/Caches/com.chrislemarquand.Ledger/thumbnails`, and the real
`~/Library/Application Support/Ledger/recent_locations.json`.

**Confirmed real damage, found and fixed**:
- `SUEnableAutomaticChecks` was left `0` (disabled) in real prefs from an
  early Phase 0.2 script iteration (before the `-disableSparkleAutoupdate`
  launch-arg fix) — restored to enabled.
- `Ledger.welcomeLastSeenVersion` was repeatedly overwritten — low-stakes,
  left as-is.
- The real **Recents list** had two polluting entries (the benchmark
  corpus path, and the LedgerUITests bundle Resources path) — removed,
  the other 8 real entries preserved exactly, verified by diff.
- The real thumbnail cache gained ~335 files (~127MB) from corpus images —
  left in place; harmless/disposable, will be naturally superseded by
  Phase 3.3's cache-bounding work.
- `ui.browser.sort` got flipped from the real `created` to `name` during
  the very re-verification run for this fix — restored. This is a
  **different, narrower residual issue**, not the same bug: see below.
- No photo files or EXIF metadata were touched at any point — this was
  entirely scoped to Ledger's own app-preference keys and cache files.

**The actual fix**: macOS's documented `NSUserDefaults` **argument
domain** — `-KeyName Value` as launch arguments (not env vars, not
`defaults write`) creates a temporary, non-persisted, per-process override
that shadows the real value for reads without touching any plist.
`run_isolated_launch` now passes
`-Ledger.welcomeLastSeenVersion "$MINOR_VERSION"` this way, dropped the
`HOME`/`mkdir`/`defaults write` entirely, and the `--trace` xctrace capture
path was fixed the same way. Verified: re-running the corrected script
left the real Recents list byte-identical (diffed before/after) and the
real preferences domain identical except for the one `ui.browser.sort`
write (see below) — a dramatic improvement over "everything leaks."

**Residual, accepted limitation**: the argument domain only shadows
*reads*. If the app itself calls `UserDefaults.standard.set(...)` during
the session — e.g. `browserSort`'s `didSet` persisting a UI-state change —
that *write* still lands in the real domain regardless of any argument-domain
override for that key. This is why `ui.browser.sort` still changed during
the corrected re-verification run even though nothing else leaked. Full
protection would need a real `UserDefaults(suiteName:)` injection point
threaded through `AppModel` and every ad hoc `UserDefaults.standard`
reference in the codebase — judged too invasive for what a benchmark
harness needs. Mitigation used and recommended going forward:
snapshot `defaults read com.chrislemarquand.Ledger` (and any relevant app
data files) before an automated run, diff after, restore anything that
changed. Also fixed at the root for the one *recurring* write this
exposed: added `-skipRecentLocationPersistence` (gates the disk write in
`persistRecentLocations()` only, in-memory behavior unaffected) since that
one would otherwise silently re-pollute Recents on every future benchmark
run — same launch-argument-gate pattern as `-disableSparkleAutoupdate`/
`-openFolderPath`.

**Consequence for prior Phase 0/1 results**: the `launch` scenario's
365.2ms median (`reports/launch-20260831-185602.md`) was measured under
the broken isolation and not re-verified — likely still approximately
correct (the Launch signpost interval completes before most
preference-dependent behavior would matter), but flagged here rather than
silently presented as clean. The `folder-load` scenario **was** re-run
under the corrected mechanism: 177.1ms median (5 iterations, corpus
unchanged) vs. the earlier, contamination-affected 169.4ms — close, within
noise, and the new number is the trustworthy one going forward
(`reports/folder-load-20260831-211905.md`; the earlier report file has
been deleted rather than left to confuse future comparisons).

Full incident detail, generalized beyond Ledger, saved to persistent
memory: `feedback_macos_home_isolation_broken`.

### Phase 2.3 detail (2026-09-01)

**What was built.** `AppModel+Quiescence.swift` (new file) adds
`isFolderWorkActive` — a computed property aggregating every known
folder-journey async source (`isFolderContentLoading`,
`isFolderMetadataLoading`, `isPreviewPreloading`, and eight `Task` properties
including two — `selectionMetadataLoadTask` and
`deferredFolderMetadataPrefetchTask` — that were themselves real,
pre-existing bugs: neither ever nilled itself on natural completion, so a
liveness check against either would have permanently read "busy" after the
very first selection change / metadata-column-enabled folder load. Fixed
both, generation-ID-guarded against a superseded task's cleanup racing ahead
of a newer one (same pattern as `folderMetadataLoadID` elsewhere in this
file) — also applied to `initialThumbnailWarmupTask`, newly promoted from a
fire-and-forget `Task.detached` to a stored, cancellable, generation-guarded
property for the same reason. `beginQuiescenceTracking(reason:)` /
`checkQuiescenceIfNeeded()` wrap this into a signpost interval, called from
`loadFiles(for:)` (folder switch/initial display), `selectionChanged()`
(selection sweep), and `browserViewMode`'s `didSet` (mode switch).

**A real instrumentation bug found and fixed before trusting any number.**
The first version scheduled an immediate self-check `Task` right after
`beginQuiescenceTracking`, reasoning "give the caller's own state change a
moment to land." `loadFiles(for:)` has a genuine `await` (its
`readBrowserFileAttributes` call, reached when `browserSort != .name` — the
default) between `beginQuiescenceTracking` and where it actually assigns
`browserItemHydrationTask`/`initialThumbnailWarmupTask`/the deferred-prefetch
tasks. The self-check `Task` won that race and ran during the gap, while
every tracked property was still `nil`, reporting quiescence ~32ms in —
confirmed by re-running after removing the self-check and getting a
dramatically different, and correct, result. Fixed by removing the immediate
self-check entirely; every real completion/cancellation site (including
"nothing to do" early returns) already calls `checkQuiescenceIfNeeded()`
itself, so a journey with truly zero work still resolves.

**Benchmark harness extended.** `run_benchmarks.sh` gained a `quiescence`
scenario (`--scenario quiescence --corpus ...`), reusing the existing
same-name begin/end interval pattern from `launch`. This surfaced a second
real bug, this time in the *harness*, not the app: opening a folder via
`-openFolderPath` on this dev machine reliably fires **two** `FolderLoad`
cycles a few milliseconds apart — very likely the app restoring its
previously-selected sidebar location on launch, moments before
`-openFolderPath` redirects to the benchmark corpus (both are legitimate,
independent folder-load journeys; `AppModel+Quiescence.swift` already tags
the interrupted one "superseded by ..." rather than reporting it as a real
duration). `extract_signpost_span_ms` was matching the *first* begin/end
pair, so it was measuring the discarded, interrupted first cycle, not the
real one. Fixed to always reset to the most recent `begin` before it looks
for that begin's `end` — correct for both same-name pairs (`launch`,
`quiescence`) and the differently-named `folder-load` pair
(`FolderLoad`→`FirstStablePaint`), and arguably improves the existing
`folder-load` number's trustworthiness too (not re-verified this pass — flag
for a future session).

**The apparent finding, and how it fell apart under investigation.** The
first trustworthy measurement showed median quiescence of **33.7 seconds**
for the 1,012-file corpus, reproducible across 5 iterations (33.5–34.2s,
tight spread — not noise). Verified independently of the signpost mechanism
via direct `ps -o %cpu` sampling every 2s across the whole window on a
manual launch: the Ledger process sustained **90–130% CPU continuously for
the full ~34s**, then dropped to near-zero — real, sustained work, not an
I/O-wait or measurement artifact. An A/B test isolating file *type* (an
80-file CR2-only subset via `ln` hardlinks vs. a 932-file JPEG+TIFF subset,
both drawn from the same corpus, both real regular files — a first attempt
using `ln -s` symlinks silently failed, since Ledger's enumeration doesn't
recognise symlinked files as supported images; the user caught this by
screenshot before any further conclusions were drawn from it) showed
quiescence scaling with **file count** (80 files → ~3.5s, 932 files →
~29.7s), not file type — ruling out "RAW decode is slow" as the cause.

That pointed at something iterating over *every* file in the just-opened
folder specifically, not the capped 56-file initial thumbnail warmup. A
targeted diagnostic signpost around the leading candidate
(`ensureSidebarImageCount`'s per-folder image count) found **zero**
invocations during the delay — ruling that out too, by direct evidence
rather than assumption. The `ExifToolProcess`/`FolderMetadataPrefetch`
signposts, which *did* fire (127 subprocess launches, exactly spanning the
full ~33.1s), gave the real answer: **`hasVisibleMetadataColumnDemand`
(Phase 2.1's demand gate) was returning `true`**, because the real
preferences domain still had `ui.icon.subtitle.column = "col-shutter"` set
— left over from testing much earlier in this session and never cleared by
the Phase 2.1 incident remediation (which only checked `ui.browser.sort`,
`SUEnableAutomaticChecks`, and Recents). Clearing that key alone didn't fix
the number, because a **second, independent** demand source was also live:
the real `Ledger.listColumns.visible` List-column preference included
`col-rating` (Rating is one of `ListColumnDefinition.metadata`), which
satisfies `hasVisibleMetadataColumnDemand`'s check regardless of which
browser view mode is active — confirmed with the user this was testing
leftover, not an intentional preference, before clearing it.

**With both cleared, quiescence for the same 1,012-file corpus is 392.2ms
median** (376–407ms across 5 iterations) — Phase 2.1's demand gate is

### Phase 2.2 detail (2026-08-31)

Audited every speculative/preload code path against the plan's four
criteria (bounded, non-competing-with-foreground, cancelled on obsolescence,
never materialises an iCloud placeholder). Findings, most to least
significant:

1. **Fixed — unbounded old-folder background warm.**
   `AppModel+Navigation.swift`'s `handleExplicitSidebarSelectionChange`
   schedules `scheduleBackgroundWarm(forSelectionID: oldID, files:...)` for
   the folder just left, keyed by sidebar ID in
   `backgroundWarmTasksBySelectionID`. The only existing cancellation was
   "if the user navigates back to that same folder, cancel its own warm
   task" (`selectSidebar`). A quick A → B → C navigation left A's warm task
   with no cancellation trigger at all once B was also left — it ran to
   completion, competing with C's now-foreground metadata/preview work for
   ExifTool subprocess slots and thumbnail-decode capacity. Fixed in
   `AppModel+MetadataPipeline.swift`'s `scheduleBackgroundWarm`: cancels
   every other entry in `backgroundWarmTasksBySelectionID` before starting
   a new one, so at most one old-folder warm task is ever in flight — only
   the most-recently-left folder, which is the only one worth keeping warm
   for a "went back" journey. Also added a per-iteration
   `isFolderMetadataLoading || isPreviewPreloading` check inside
   `warmCachesInBackground`'s metadata and preview loops (previously only
   checked twice, at the very start of the function) so the task yields
   mid-run the moment real foreground work begins, not just before it
   starts.
2. **Already compliant — iCloud placeholder safety.** Both prefetch paths
   (`readMetadataBatchResilient` for metadata, `ThumbnailService`'s cold
   path for previews/thumbnails) already skip/avoid materialising
   placeholders — the metadata path filters them out entirely, and
   `ThumbnailService` falls back to `QLThumbnailGenerator` (which can
   preview a placeholder without downloading it) instead of the
   `CGImageSource` path that would force a full iCloud download. No change
   needed; this protects speculative work by construction, not by a
   speculative-work-specific check.
3. **Already compliant — inspector-neighbor preload is bounded.**
   `previewPreloadCandidates` caps to a ±10-index radius around each
   selected file and a 64-item overall cap (`previewPreloadNeighborRadius`,
   `maxPreviewPreloadCandidates`), sorted by distance from the primary
   selection so the closest neighbors win the cap. No unbounded case found.
4. **Already compliant — deferred preview preload.** Already gated behind
   `scheduleDeferredPreviewPreload`'s debounce delay and gets fully
   cancelled at the top of `loadFiles(for:)` on every folder switch (`
   previewPreloadTask`, `deferredPreviewPreloadTask`,`previewPreloadID`
   rotation) — this was already correct before 2.2, including after the
   2.1 gating change.
5. **Not applicable — "closing/detaching the window" cancellation.**
   Ledger is a single-window app; `AppDelegate.
   applicationShouldTerminateAfterLastWindowClosed` already returns `true`,
   and there is no multi-window/tab/detach concept in this codebase. Window
   close already terminates the process, which tears down every in-flight
   `Task` (including `backgroundWarmTasksBySelectionID`) for free. Building
   an `NSWindowDelegate`-based cancellation path for a scenario that cannot
   occur was judged over-engineering; noted here so a future session
   doesn't wonder why it's missing.
6. **No dedicated "initial thumbnail warmup" feature exists** distinct from
   `NSCollectionViewPrefetching`'s standard viewport-driven prefetch
   (`BrowserIconView.swift`), which is already bounded by the OS API to
   near-visible cells only — nothing eager or whole-folder to gate here.

Verified via `xcodebuild build`/`xcodebuild test -scheme Ledger` on
`SharedUI.xcworkspace` (full unit suite + all 4 `LedgerUITests` cases
green) after the `scheduleBackgroundWarm`/`warmCachesInBackground` changes.

### Phase 3.1 detail (2026-09-02)

`metadataByFile: [URL: FileMetadataSnapshot]` accumulated an entry for every
file whose metadata was ever read, for the entire app session — `loadFiles`'s
`clearLoadedContentState(preserveSessionCaches: true, ...)` call on every
folder switch deliberately preserves it (so returning to a folder doesn't
re-read from disk), but nothing ever trimmed it. `inspectorPreviewImages`
already had exactly this kind of bound (`maxInspectorPreviewCacheEntries`,
`inspectorPreviewRecency` + `trimInspectorPreviewCacheIfNeeded()`) — this
phase gives `metadataByFile` the same treatment.

**What was built**, both in `AppModel+MetadataPipeline.swift`:
- `Self.maxMetadataCacheEntries = 5000` (`AppModel.swift`) — a documented,
  adjustable cap. Chosen as "a handful of average folders' worth" relative
  to the Phase 0.4 benchmark corpus (1,012 files); most real folders are far
  smaller. Not derived from a measured memory budget (see "not yet done"
  below) — a reasonable starting point, not a rigorously justified number.
- `mergeMetadataSnapshots(_:into:)` — a shared merge step (previously
  duplicated near-identically across 4 call sites in
  `AppModel+MetadataPipeline.swift`, `AppModel+Navigation.swift`, and
  `AppModel+FileLoading.swift`... actually `AppModel+Import.swift` — see
  below) that folds snapshots into a map, clears their
  `staleMetadataFiles`/`pendingCommitsByFile` markers, and records a
  load timestamp in the new `metadataLastLoadedAt: [URL: Date]`.
  `AppModel+Import.swift`'s `importMetadataSnapshots` has slightly different
  semantics (builds a separate `result` dict, doesn't clear
  `pendingCommitsByFile`) so it was left as its own loop, just with the
  timestamp bookkeeping added directly rather than forced through the
  shared helper.
- `trimMetadataCacheIfNeeded()` — called after every site that assigns to
  `metadataByFile`. Evicts oldest-by-`metadataLastLoadedAt` entries once the
  count exceeds the cap, protecting: `selectedFileURLs`, `browserItems`
  (the active folder), `pendingEditsByFile`/`pendingImageOpsByFile` keys,
  `pendingCommitsByFile` keys, and `staleMetadataFiles` — exactly the plan's
  "current selection, active folder, pending edits, undo/restore
  requirements, and in-flight operations" list. Undo/redo itself needs no
  protection: `PendingEditState` (the undo/redo stack's element type) is
  self-contained and doesn't read back through `metadataByFile`.
- **Recency proxy, a deliberate simplification**: "last freshly loaded from
  ExifTool", not "last read from the dictionary". A true LRU would need
  intercepting every one of the many direct `metadataByFile[url]` read
  sites across the app (inspector fields, undo status, editing, date/time
  adjust, etc.) — this proxy still favours recently-visited folders' data,
  which is what "resident memory plateaus" actually needs, without that
  invasive a change.

**Verified with two new unit tests** in `Tests/LedgerTests/AppModelTests.swift`:
`testMetadataCacheEvictsOldestUnprotectedEntriesOnceOverCapacity` (populates

## Robustness checklists

Concrete verification steps for the phases that introduce new concurrent code
or touch the AppKit/SwiftUI bridge. Swift 6 strict concurrency is already on
(`Config/Base.xcconfig`), so compiler-checked Sendable/data-race issues are
largely covered already — these checklists cover what the compiler can't
verify: cancellation correctness and bridge lifecycle hygiene.

### New async paths (1.1 thumbnail broker, 2.1 demand-order metadata loader)

- [ ] Every launched `Task` for a folder/selection/visible-set request is
      stored and explicitly cancelled on folder switch, selection change,
      view detach, and window close — no orphaned task outlives its request.
- [ ] Loop bodies over batches (thumbnail decode, metadata batches) call
      `Task.checkCancellation()` or check `Task.isCancelled` between items,
      not just once at the start.
- [ ] Cancellation is silent (`CancellationError` swallowed) and does not
      surface as a user-visible error or log spam.
- [ ] Cache/broker state mutated from both the async path and the main actor
      has a single clear isolation boundary (actor or `@MainActor`), not an
      ad hoc lock — verify this at the point the synchronous fast path (1.1)
      meets the new async slow path.

### Hosted SwiftUI bridge (1.2 render routing, 1.4 lifecycle, 4.1 menu ownership)

- [ ] Every Combine `.sink` / observation closure in a bridge controller
      captures `[weak self]`.
- [ ] Every subscription/observer installed in `viewDidLoad`/`init` is
      cancelled/removed in the matching teardown (`deinit` or explicit
      dismantle) — matches the plan's own 1.4 "symmetric install/teardown"
      requirement, called out here as a literal grep-for-`store(in:)`-vs-
      teardown check per bridge file.
- [ ] `NSHostingView`/`NSHostingController` instances that are hidden
      (inactive browser mode, non-frontmost pane) are not sent new
      `rootView` values — confirms 1.2's "do not recreate or update hidden
      hosted SwiftUI roots" is actually verifiable via a counter, not just
      asserted.
- [ ] No hosted SwiftUI pane/sheet construction path can run before the 4.1
      static menu builder — check this explicitly on every code path that
      creates a hosting controller during launch, not just the primary one.

## Phase 0.4 progress: browse corpus, folder-load scenario, xctrace capture

Generated the plan-required >=1000-file browse corpus with
`scripts/performance/generate_browse_corpus.sh` (gitignored output,
`scripts/performance/corpus/`; regenerate with `--force`): 900 duplicated/
renamed JPEGs (40 unique sources from the two user-provided Downloads
folders), the 12 original TIFFs from "Ledger Import Test Large" (not
duplicated — ~180MB each), and 100 real RAW files (80 CR2 + 20 JPG) copied
from `~/Library/Mobile Documents/.../Capture - iCloud Drive/Home` (confirmed
already fully materialized locally before copying, not iCloud placeholders —
copying a placeholder would force a download). 1,012 files, 9.1GB total.
Never writes to or modifies any of the three source locations.

Extended `run_benchmarks.sh` with a `folder-load` scenario (`--scenario
folder-load --corpus scripts/performance/corpus/browse`) and a `--trace`
flag that captures one real `xctrace record --template 'Time Profiler'`
trace via its `--launch`/`--env` support (not counted in the measured
iterations). **Result: median 169.4ms folder-load (folder-load-begin → first
stable paint) over 5 iterations against the 1,012-file corpus**, see
`scripts/performance/reports/folder-load-20260831-200950.md`.

**Two real bugs found and fixed in production code while validating this —
not just script bugs, actual Phase 0.1 instrumentation defects — both in
`BrowserContainerViewController.swift`:**

1. The original `FirstStablePaint` signpost required observing an explicit
   `.loading` overlay state before it would fire on the transition away from
   it. A folder load fast enough to complete before the render coalescer's
   next pass (enumeration alone, before per-item attribute hydration, is
   fast even for 1,012 files) never surfaces `.loading` as an intermediate
   state at all — so the signal silently never fired. Fixed by tracking
   `hasPaintedCurrentLoad` (reset on `selectedSidebarID` change, not on
   observing `.loading`) instead of requiring the transition.
2. That fix alone caused a second bug: `selectedSidebarID` changes
   synchronously, but the actual `loadFiles()` call that does the real work
   runs on a separately-scheduled `Task`, so the *first* `render()` pass
   after a selection change can read stale "nothing loading, nothing loaded"
   state and fire `FirstStablePaint` immediately — before the real load even
   started. Fixed with `renderPassesSinceSelection`, requiring more than one
   render pass since the selection changed before treating a settled state
   as final.

Both verified by direct inspection of the raw signpost timeline (`FolderLoad
begin`/`FirstStablePaint event` timestamps), not just by the benchmark
script producing a number — a plausible-looking number was exactly how bug
2 was hiding behind bug 1's fix. Full regression suite (208 tests, 0
failures) re-run and confirmed green after both fixes.

**xctrace quirk recorded for future reference:** `xcrun xctrace record`
exits non-zero when its `--time-limit` forcibly ends the launched process,
even on a fully successful capture (verified: the log says "Recording
completed. Saving output file..." on the same run reporting a non-zero
exit). The script checks for the `.trace` output existing, not the exit
code.

## Phase 0.4 progress: B22 warning repro attempt

Investigated 2026-08-31: does "Publishing changes from within view updates
is not allowed" still reproduce after the AppKit sidebar migration? Wrote a
throwaway `LedgerUITests` test that launched a Debug build and rapidly
switched the sidebar selection Desktop→Downloads→Pictures three times (the
exact interaction category `ROADMAPOLD.MD` B14/B22 implicated —
`.onChange(of: model.selectedSidebarID)`), while capturing
`log stream --predicate 'eventMessage CONTAINS "Publishing changes" OR eventMessage CONTAINS "reentrantly"'`
in parallel. Zero matches across a full run. Result recorded in
`ROADMAPOLD.MD`: B22 marked superseded.

**Automation lesson (distinct from Phase 0.3's sandbox-write-visibility
finding): clicking a sidebar shortcut for a TCC-protected folder
(Desktop/Downloads/Documents/Pictures) triggers a real macOS privacy
dialog that blocks headlessly and re-prompts on every build** — the UI
test runner gets a fresh ad-hoc code signature each build, and TCC keys
its one-time-approval memory off that identity, so approving it once does
not stick for the next run. This is a harder blocker than the App Sandbox
one from 0.3: there is no launch argument or entitlement that suppresses a
TCC prompt from inside the app being tested. The investigative test was
removed from the permanent suite after one manual run rather than left in
automated rotation — see the comment left in `LedgerUITests.swift` in its
place. **Any future UI test or benchmark scenario must avoid triggering
sidebar/file access to Desktop, Downloads, Documents, or Pictures** unless
a real fix is found (e.g. confirming `tccutil`/pre-authorizing the app's
stable identity actually survives rebuilds — not verified, don't assume it
works). The bundled `LedgerUITests/Fixtures/` folder and any future scenario
using it are fine precisely because they live inside the app bundle, not
under one of the TCC-protected user folders.
