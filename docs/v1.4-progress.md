Five real things were discovered only by actually running this against the
built app (none guessable from source):
1. **`LedgerUITests-Runner` is sandboxed** with read-only access to all of
   `/` but write access only inside its own container (confirmed via
   `codesign -d --entitlements -`). This blocks the obvious approach of
   having the test process copy fixture images to a shared writable temp
   location — `FileManager.default.temporaryDirectory` is invisible to the
   separately-launched, unsandboxed Ledger process ("Folder Unavailable"),
   and a hardcoded `/tmp` path is flatly denied to the sandboxed test host
   ("Operation not permitted"). Fix for the read-only journeys implemented
   here: point `-openFolderPath` directly at the test bundle's own Resources
   folder (`Bundle(for: Self.self).resourceURL!`) — no copying, since the
   sandboxed host can read anywhere. A write-capable journey (metadata
   apply/restore) has no equivalent easy fix and is deferred.
2. Per (1), **HOME isolation isn't achievable for UI tests** the way
   `scripts/performance/run_benchmarks.sh` does it for direct-executable
   launches — same container-isolation blocks it. UI tests run against your
   real, developer-machine Ledger preferences. Consequence: **running these
   tests may change your last-used view mode/sort order in Ledger.** Nothing
   about file contents, metadata, or data is touched.
3. The view-mode segment's real accessibility label is **"Icon"** (singular)
   — the source's `labels: ["Icons", "List", "Gallery"]` array in
   `MainContentView.swift` does not match what AppKit actually exposes.
   Caught by dumping the real accessibility hierarchy
   (`app.debugDescription`) rather than guessing from source, which is the
   general lesson here: write one exploratory dump test against a live
   launch before authoring real locators for any new UI-test journey.
4. The Sort toolbar item is an `XCUIElement.ElementType.menuButton`, not
   `.button` — `app.buttons["Sort"]` silently never matches.
5. **The Sparkle background-update check was not actually suppressed** —
   the update window appeared on every launch despite seeding
   `SUEnableAutomaticChecks` via `defaults write` (Phase 0.2's approach).
   Replaced with a real launch argument, `-disableSparkleAutoupdate`,
   gating the call to `updateService?.performBackgroundCheck()` directly in
   `LedgerApp.swift` — reliable because it's in code, not hoping Sparkle
   honors a preference. Both `run_benchmarks.sh` and `LedgerUITests.swift`
   now pass this flag. If you ever see the Sparkle window during a
   benchmark/test run again, this is the first place to check.

**Bugs found and fixed while validating 0.2 against a real run — all three
would have made the runner silently hang or misreport, so treat this list as
required reading before trusting output from a *new* scenario added later:**
1. `log stream` excludes signpost events by default even at `--level info`
   — needs an explicit `--signpost` flag. Verified the real ndjson field
   shape (`signpostName`, `signpostType: begin/event/end`; `eventMessage` is
   always empty for signposts) via a manual probe capture before trusting
   the parser.
2. `pid=$(some_function_that_backgrounds_a_process)` blocks until that
   background process *exits* — it inherits the command substitution's
   stdout pipe, so `$(...)` doesn't return on EOF until every holder of that
   pipe's write end closes it, including the long-lived GUI process. Fixed
   by redirecting the launched app's stdout/stderr to `/dev/null` inside
   `run_isolated_launch`. This is a general trap for any future scenario
   function that backgrounds+captures-PID in one call — always redirect the
   backgrounded command's own stdout/stderr away from the enclosing
   function's stdout.
3. A bare `kill "$pid"; wait "$pid"` hung indefinitely in this machine's
   system bash (3.2) when `$pid` came from a command-substitution subshell.
   Fixed with a bounded poll-then-SIGKILL helper (`terminate_process`),
   mirroring `scripts/release/release_check.sh`'s existing `run_with_timeout`
   pattern rather than inventing a new one.

Also: macOS ships bash 3.2, not bash 4.3+ — `local -n` namerefs don't exist.
`median()` takes array elements as positional args instead.

### Phase 1.1 detail

`ThumbnailService.cachedImage(for:minRenderedSide:)` fell back from the
memory `NSCache` to a synchronous `readDiskCache` call (`FileManager`
existence + mtime stat, then `NSImage(contentsOf:)` decode) on a memory-cache
miss — real disk I/O and image decode running inline on whatever thread
called it.

Used a fork to classify all 19 call sites first rather than guess scope:
13 were genuine synchronous UI hot paths (List/Icon/Filmstrip cell
configuration via `NSCollectionViewDataSource`/table cell-config methods,
plus the aspect-ratio helpers and per-cell `requestThumbnail` guard checks
those call into; and the inspector/large-preview chain reached synchronously
from `collectionView(_:didSelectItemsAt:)` via `loadInspectorPreview`), 2
were `NSCollectionViewPrefetching` callbacks (main-thread-dispatched by
AppKit but for off-screen rows, lower priority), and 6 were already safely
inside async `Task` contexts or explicit background-warm functions.

Fix: stripped the disk fallback out of `cachedImage` itself — it's now
memory-cache-only — rather than rewriting all 13 hot-path call sites
individually. Every one of them already had an async `request()` fallback
wired up for the "not cached" case (that's the existing two-tier
check-then-request pattern used throughout the browser views), so a
memory-cache miss now correctly falls through to the path that was already
there instead of doing its own disk read. `readDiskCache` remains reachable
from the async `generate()` path (inside the broker), so disk-cache hits are
still honored — just asynchronously.

**This is a compile-time-verifiable guarantee, not an empirical one**:
`readDiskCache` is a `private static func` in `ThumbnailService.swift`, and
grepping the file confirms its only two callers are the now-fixed
`cachedImage` (removed) and `generate` (already async, inside
`broker.request`). No other synchronous disk I/O (`NSImage(contentsOf:`,
`FileManager.default.fileExists`, `Data(contentsOf:`, etc.) exists anywhere
in the four hot-path files (`BrowserIconView.swift`, `BrowserListView.swift`,
`BrowserFilmstripViewController.swift`, `AppModel+MetadataPipeline.swift`) —
confirmed by grep, not just reasoning about this one function.

Accepted trade-off (the plan's own framing): a thumbnail that's warm on disk
but was evicted from the in-memory `NSCache` (app relaunch, memory pressure)
now shows a placeholder/fallback icon for one more render pass instead of
appearing synchronously, rather than blocking cell configuration to avoid
that frame.

Full regression suite re-confirmed green (208 tests, 0 failures) after the
change. Not yet done: the plan's fuller manual test matrix (cold/warm cache,
corrupt cache entries, internal/external volumes, memory pressure,
cancellation) — the automated tests don't specifically exercise disk-cache
eviction/corruption scenarios. A `--trace` Time Profiler capture during the
`folder-load` benchmark scenario exists (`scripts/performance/output/raw/.../*.trace`,
gitignored) as manual-review evidence if wanted, though the structural
grep-based guarantee above is stronger than what a single profiling run
could show empirically.

### Phase 1.2 detail

`BrowserContainerViewController.render()` called `.update(model:items:)` on
all three of `iconController`/`listController`/`filmstripController`
unconditionally on every render, regardless of which one `model.browserViewMode`
actually made visible — confirmed these are the *only* path driving those
controllers (grepped for independent Combine subscriptions inside
`BrowserIconView.swift`/`BrowserListView.swift`/`BrowserFilmstripViewController.swift`;
none exist, everything comes through the container). This exactly matched
the plan's own cited example: Filmstrip's `update()` set
`previewHostingView.rootView = LargePreviewPane(model: model)` (a hosted
SwiftUI root) at the very top, before its own guard checking whether Gallery
was even the active mode — so that hosted root was being replaced on every
render while Gallery was hidden.

Fix: `render()` now `switch`es on `model.browserViewMode` and calls
`.update()` on only the matching controller. Because `applyBrowserModeIfNeeded`
(which swaps view visibility) runs earlier in the same `render()` call,
`model.browserViewMode` is already current by the time the switch runs — a
mode switch's newly-active controller gets a correct, immediate update on
the very same render pass, no staleness window. This resolves the Filmstrip
hosting-root case as a side effect, not a separate fix: with the switch in
place, `filmstripController.update()` (and therefore the `previewHostingView.rootView`
assignment) simply isn't called at all while Gallery isn't active.

Like Phase 1.1, the "no render work in hidden surfaces" guarantee here is
structural (a `switch` can only take one branch) rather than something
proven only by a counter. Verified via the full regression suite, including
`LedgerUITests.testBrowserViewModeSwitching`, which exercises exactly this
code path (Icon→List→Gallery→Icon) and confirms no staleness was introduced.

**Explicitly not done, pending trace evidence per the plan's own
instruction** ("Prefer a small revision or changed-URL set over a complete
high-churn dictionary **when traces show the dictionary publication is
material**"):
- Removing redundant observation between `$browserItems` and
  `$filteredBrowserItems` in `installRenderObservers()` — both are observed
  separately, but a `$browserItems` change likely always implies a
  `$filteredBrowserItems` change too. Combine's synchronous re-entrant
  publishing plus the existing `MainActorCoalescer` probably already
  collapses these into one actual `render()` call in practice, meaning the
  fix might not be worth the complexity — not measured either way yet.
- Replacing `$metadataByFile`'s full-dictionary publication with a smaller
  revision/changed-URL set. No trace evidence yet showing this dictionary's
  publication is actually material to render cost; doing this without that
  evidence would be exactly the kind of unproven structural change the plan
  warns against.
- Temporary render/inactive-update/hosting-root-replacement counters the
  plan suggests adding — skipped because the fix already makes the thing
  they'd count structurally impossible (same reasoning as Phase 1.1's
  compile-time-verifiable framing), so there's nothing left to counter-verify
  empirically. Revisit if a future profiling pass wants call-frequency data
  for a different reason (e.g. investigating render() firing too often in
  general, independent of which controller it targets).

### Phase 1.3 detail: hangs/hitches capture workflow

**What's automatable vs. not, decided empirically this round:**
- Trace *capture* (Time Profiler; Animation Hitches is the other directly
  relevant template — there's no standalone "Hangs" template, hang
  detection lives inside Time Profiler's `potential-hangs`/`hang-risks`
  tables) is fully automatable via `xctrace record --attach <pid>`.
- Driving the interaction itself via `osascript`/System Events proved too
  flaky to rely on: AX property reads (`title of radio button ...`)
  intermittently returned real values ("Icon") and then `missing value` on
  the next query with no code change, and the window's title changes
  dynamically during folder load in a way that broke cached AppleScript
  object references mid-script. Not worth fighting — the user does the
  interaction manually instead, which is both more reliable and exercises
  the real thing (a script clicking a button isn't quite the same signal
  as a human actually using the app).
- **Live resize is explicitly not worth automating even if it could be
  forced via AppleScript's `set bounds`** — that would be a discrete
  frame-set, not a continuous drag, and wouldn't reproduce the actual
  bug class (repeated layout passes *during* a drag).
- Metadata writes remain blocked by Phase 0.3's sandboxed-write-visibility
  finding (no location both a test harness and Ledger can write to without
  real design work).

**Working hybrid workflow** (repeatable for the remaining journeys):
1. Launch Ledger directly (not through XCUITest) with the browse corpus
   open, same isolated-HOME approach as `run_benchmarks.sh`.
2. Poll `osascript -e 'tell application "System Events" to tell process
   "Ledger" to return name of window 1'` until the title stops showing
   "Loading" — reading a property this way was reliable even though
   clicking wasn't.
3. Start `xcrun xctrace record --template 'Time Profiler' --attach <pid>
   --time-limit Ns --output foo.trace --no-prompt` in the background, and
   in the same turn ask the user to perform the interaction sequence live
   — the ask needs to land in the same message as starting the capture so
   the timing lines up.
4. `xcrun xctrace export --input foo.trace --xpath '/trace-toc/run[@number="1"]/data/table[@schema="potential-hangs"]'`
   gives hang start-time/duration/thread directly as XML — genuinely
   useful without opening Instruments. Cross-reference a hang's timestamp
   against the `time-profile` table's `sample-time` (same query pattern,
   filtered to the `<thread ref="N"/>` matching Main Thread — find N via
   `grep -o '<thread id="[0-9]*"[^/]*fmt="[^"]*Main Thread[^"]*"'`) to pull
   the actual call stack during the hang window.

**First real capture (2026-08-31), partial interaction coverage** — the
user got through scrolling and part of the mode-switching/selection list
before time ran out, not the full sequence (pane toggle, menu open, and
possibly live resize were attempted but not confirmed complete). Found:
two genuine main-thread "Microhang" entries in `potential-hangs`, ~300ms
each, ~900ms apart, around the 45–47s mark. Pulled the call stacks for

— consistent with a window resize or titlebar drag, not app code. Only
**one** frame in the entire hang window's stacks mentioned Ledger code
(`BrowserContainerViewController`, incidental). **Read as: this specific
hang is AppKit/SwiftUI's own window-interaction cost, not a Ledger defect
in the areas Phase 1 targets** — matches the plan's own framing of live-resize
cost as a largely system-level category. No code change indicated from
this data alone.

## Robustness checklists

Concrete verification steps for the phases that introduce new concurrent code
or touch the AppKit/SwiftUI bridge. Swift 6 strict concurrency is already on
(`Config/Base.xcconfig`), so compiler-checked Sendable/data-race issues are
largely covered already — these checklists cover what the compiler can't
verify: cancellation correctness and bridge lifecycle hygiene.

### New async paths (1.1 thumbnail broker, 2.1 demand-order metadata loader)

- [ ] Every launched `Task` for a folder/selection/visible-set request is
      stored and explicitly cancelled on folder switch, selection change,
      view detach, and window close — no orphaned task outlives its request.
- [ ] Loop bodies over batches (thumbnail decode, metadata batches) call
      `Task.checkCancellation()` or check `Task.isCancelled` between items,
      not just once at the start.
- [ ] Cancellation is silent (`CancellationError` swallowed) and does not
      surface as a user-visible error or log spam.
- [ ] Cache/broker state mutated from both the async path and the main actor
      has a single clear isolation boundary (actor or `@MainActor`), not an
      ad hoc lock — verify this at the point the synchronous fast path (1.1)
      meets the new async slow path.

### Hosted SwiftUI bridge (1.2 render routing, 1.4 lifecycle, 4.1 menu ownership)

- [ ] Every Combine `.sink` / observation closure in a bridge controller
      captures `[weak self]`.
- [ ] Every subscription/observer installed in `viewDidLoad`/`init` is
      cancelled/removed in the matching teardown (`deinit` or explicit
      dismantle) — matches the plan's own 1.4 "symmetric install/teardown"
      requirement, called out here as a literal grep-for-`store(in:)`-vs-
      teardown check per bridge file.
- [ ] `NSHostingView`/`NSHostingController` instances that are hidden
      (inactive browser mode, non-frontmost pane) are not sent new
      `rootView` values — confirms 1.2's "do not recreate or update hidden
      hosted SwiftUI roots" is actually verifiable via a counter, not just
      asserted.
- [ ] No hosted SwiftUI pane/sheet construction path can run before the 4.1
      static menu builder — check this explicitly on every code path that
      creates a hosting controller during launch, not just the primary one.

iterations). **Result: median 169.4ms folder-load (folder-load-begin → first
stable paint) over 5 iterations against the 1,012-file corpus**, see
`scripts/performance/reports/folder-load-20260831-200950.md`.

**Two real bugs found and fixed in production code while validating this —
not just script bugs, actual Phase 0.1 instrumentation defects — both in
`BrowserContainerViewController.swift`:**

1. The original `FirstStablePaint` signpost required observing an explicit
   `.loading` overlay state before it would fire on the transition away from
   it. A folder load fast enough to complete before the render coalescer's
   next pass (enumeration alone, before per-item attribute hydration, is
   fast even for 1,012 files) never surfaces `.loading` as an intermediate
   state at all — so the signal silently never fired. Fixed by tracking
   `hasPaintedCurrentLoad` (reset on `selectedSidebarID` change, not on
   observing `.loading`) instead of requiring the transition.
2. That fix alone caused a second bug: `selectedSidebarID` changes
   synchronously, but the actual `loadFiles()` call that does the real work
   runs on a separately-scheduled `Task`, so the *first* `render()` pass
   after a selection change can read stale "nothing loading, nothing loaded"
   state and fire `FirstStablePaint` immediately — before the real load even
   started. Fixed with `renderPassesSinceSelection`, requiring more than one
   render pass since the selection changed before treating a settled state
   as final.

Both verified by direct inspection of the raw signpost timeline (`FolderLoad
begin`/`FirstStablePaint event` timestamps), not just by the benchmark
script producing a number — a plausible-looking number was exactly how bug
2 was hiding behind bug 1's fix. Full regression suite (208 tests, 0
failures) re-run and confirmed green after both fixes.

**xctrace quirk recorded for future reference:** `xcrun xctrace record`
exits non-zero when its `--time-limit` forcibly ends the launched process,
even on a fully successful capture (verified: the log says "Recording
completed. Saving output file..." on the same run reporting a non-zero
exit). The script checks for the `.trace` output existing, not the exit
code.

sidebar/file access to Desktop, Downloads, Documents, or Pictures** unless
a real fix is found (e.g. confirming `tccutil`/pre-authorizing the app's
stable identity actually survives rebuilds — not verified, don't assume it
works). The bundled `LedgerUITests/Fixtures/` folder and any future scenario
using it are fine precisely because they live inside the app bundle, not
under one of the TCC-protected user folders.
